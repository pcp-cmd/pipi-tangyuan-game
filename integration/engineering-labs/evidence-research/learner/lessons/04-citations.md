# 第四站：引用是真的，回答仍可能错

目标：把原句身份、结构化字段支持、版本与替代关系分开检查。

## 先做两个不同的判定

运行 `python examples/toy_walkthrough.py quotes`。异题资料写 `rental_end = 17:00`，问题问 `rental_start`。原句身份检查会成功，因为句子确实在文本里；回答支持检查应失败，因为租赁结束不是开始。

自己再写一个真 id、假句子，以及一个假 id、真句子。实现 `validate_quote` 时依次验证提案形状、非空 span、id、原文切片。返回 reason 指向真正失败处，不把所有错误说成“模型不聪明”。quote 的 hash 另对 UTF-8 bytes 算，文档 hash 仍绑定整文件。

## 这次只处理可检查的完整字段行

本工程采用 `field = value` 的窄语法。值可能含 `; only booked visitors` 等条件，必须完整保留。把 `rental_start = 08:00 ; members only` 摘成 `rental_start = 08:00`，子串检查可以成功，但支持检查应拒绝，因为丢了条件。

用 `re.fullmatch` 检查整行，或者逐字符检查同样的 grammar。还要确认 start 前是文本开头或换行，end 后是文本结尾或换行。proposal.answer 必须等于完整值；发布者、版本、hash 由宿主文档生成，不能由提案选择。

这并不识别任意自然语言。例如“到场前应预约”和“仅预约者可入内”可能有关，但我们的字段匹配没有证明这层含义。自由总结仍需独立判断任务支持、来源质量和限定条件。

## 明示替代与不能消除的冲突

异题旧通知：租赁处说押金 3。新通知：同租赁处、更晚发布、已经生效、supersedes 明示旧 id，说押金 4。四个条件同时成立才消掉旧值。另一个博客即使更晚，也不能凭日期或自称官方覆盖原通知。两份活跃资料值不同就保留 conflict 和各自引用。

再造撤回通知：明确替代旧通知，却没有新押金值。这时应 unknown，不能继续沿用旧值。未来生效的通知今天不替代现行规则。声明的实验信任元数据并没有验证现实发布者身份。

写 `resolve`，对重复检索到同一文档/版本/span 去重；两个来源恰好都写同值，只表示当前值一致，不意味着两个独立事实证据。保留 discarded 引用及 replaced_by 供追查。

## 练习和排错

对应 EvidenceContract。若一个断言“真原句答错字段”失败，不要增强 hash；它已经是正确原句，需要修支持关系。若其他发布者消掉冲突，检查 issuer 和明示替代条件。若旧来源 hash 被覆盖，回到文档读取时保存每条自己的版本。

独立应用：写一份“周末例外”通知，先故意截掉条件通过身份检查，再让支持检查拒绝。记下两层检查的不同结论，不能只交最终绿色结果。
