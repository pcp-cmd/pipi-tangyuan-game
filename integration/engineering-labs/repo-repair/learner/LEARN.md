# 从读懂一份文件，到交付一次可信的改变

按顺序完成下面七站。每站先预测结果，再运行自己的最小实验，最后写工程函数。需要帮助时先读“思路”，仍卡住再读“定位”；不要先把工程参考实现贴进编辑器。

## 第一站：解释器、目录和版本分别是谁

终端中的 `python` 是一个入口，不是“这个项目的 Python”。`sys.executable` 告诉你当前进程的解释器位置，`Path.cwd()` 告诉你当前目录；Git 保存的源码版本又是另一件事。三者都记录，排错时才能判断变的是代码还是环境。

先写 `where_am_i.py`，只输出这两个位置和 `sys.version`。如果想试虚拟环境，在本练习目录用 `python -m venv --without-pip .venv` 建一个不安装任何包的环境，再用其中的解释器运行同一文件。Linux/macOS 入口通常是 `.venv/bin/python`；Windows 是 `.venv\Scripts\python.exe`。只有实际成功运行后才填写结果。

预测：换一个工作目录后，解释器路径一定改变吗？在虚拟环境内运行，程序就不能读取外部文件了吗？第二问将在第六站用自己创建的无害文件验证。

**思路：** 用一个变量一次只改变一个条件。

**定位：** 两次命令都给脚本的准确位置，比较解释器、cwd、版本三个字段，不凭终端前面的环境名称判断。

## 第二站：先读当前字节，再谈修改

字符串适合解释文字；字节适合判断磁盘内容是否改变。UTF-8 中文字符常占多个字节，所以“65,536 个字符”和“65,536 字节”不是一个限制。`\r\n` 与 `\n` 看起来都换行，原始字节却不同。

异题实验：建一个 `航线.txt`，用 `write_bytes("东港\r\n北湾\r\n".encode("utf-8"))` 写入。读回 `bytes`，计算 `hashlib.sha256(data).hexdigest()`，严格解码后检查文字。只改一个换行，再比较摘要和字节数。摘要能发现改动，不能证明作者是谁，也不是授权。

实现 `read_snapshot` 前，先在纸上写出路径规则：只接受相对 `/` 路径；没有 `..`、反斜杠、盘符或空组件；逐级拒绝链接；根目录由宿主提供。不要把 `root / name` 当成完成了范围检查。读取前检查与写入之间仍可能竞争，本练习的临时仓库采用单写入者；这不是对抗任意并发进程的安全服务。

**思路：** 范围检查、字节限制、解码失败分别处理。

**定位：** 读取最多“上限加一”字节可以判断超长，没必要先把任意大文件全部加载。不要用广泛 `except` 把权限错误悄悄当成没有文件。

### 一个文件也可能有两个名字

`Path.resolve()` 能整理路径并跟随符号链接。硬链接是另一种情况：两个不同名字可以指向同一份文件。比较两个字符串不能证明它们不同。先在你自己的临时目录写 `a.txt`，用 `os.link("a.txt", "b.txt")` 建立另一个名字；观察两个 resolve 结果不同，但 `Path("a.txt").samefile("b.txt")` 为真。只在支持硬链接的文件系统做这个实验，不操作真实资料。

`samefile` 要求两个文件都能被访问，否则可能抛出 `OSError`。输出还不存在时不直接调用它。预测一下：如果工具承诺不把输入当作输出，应该比较文件名字，还是实际文件身份？先写会拒绝这种别名的测试，再补你的实现。Linux 上做过此实验不代表 Windows 上已经验收。

## 第三站：搜索只是线索，提议还没有写入

先列目录，再按关键词找出行号，最后读取完整文件。一个词在手册出现，不等于那份手册允许改；搜索到两处代码也不等于应该同时替换。

异题实验：维修清单写两次“灯泡待换”。用 `text.count(old)` 预测替换数量。如果只允许修其中一行，增加包含邻行的上下文，直到旧片段唯一。用 `difflib.unified_diff` 生成提议，检查未修改部分是否保持原样。这里不提供仓库题的修复字段。

你的补丁提议应包含路径、读取时摘要、旧片段、新片段和真实 diff。它不能写文件。执行前再读一次当前摘要：如果另一人加了注释，就返回冲突，让人重新审阅，不能拿旧全文覆盖掉新注释。

**思路：** 把“可以提出”与“已经执行”做成两个函数。

**定位：** 用“唯一旧片段 + 当前摘要 + 写入允许清单”共同约束一次修改；其中任意一个通过都不能代替另外两个。

## 第四站：批准的是这次动作

批准由宿主的 `approve` 回调产生，不能从 README、工具输出或模型决策中拿一个 `approved: true` 代替。批准绑定操作者、动作和准确参数，还带到期时间与一次性标识。

异题实验：旅客批准“租一把黄色雨伞两小时”，商家把颜色换成红色后还能沿用原批准吗？把参数字典排序、稳定编码并算摘要，可以让两边比较同一内容；它只是本地合同绑定，不能让模型自己生成的摘要变成可信批准。授权来源仍由宿主把握。

本练习规定 `now == expires_at` 已到期，布尔值不能冒充整数时间。每种错误用新批准验证，避免“已用过”先拒绝，反而没测到参数错或过期。

写入采用唯一临时文件、完整写完、替换目标并读回，不能固定用 `app.pending` 踩掉别人的文件。已进入写入尝试的批准被消费；I/O 失败后重新读取并重新批准。示例只承诺单文件操作，不声称跨文件事务或掉电后所有目录元数据都已持久化。

## 第五站：测试结果属于哪一版

先保存原测试的摘要。补丁修改业务源码，验收入口与原测试仍由验收方保留。测试前后都核对；如果断言被删了，不能用“当前测试通过”取代原要求。

观察四个不同结果：输出写 `PASSED` 但退出状态为 1；退出为 0 但一项测试都没运行；确实运行却有失败；真实检查全过但源码之后又改了。它们不能归成一种“成功”。

公开检查的 `fixture.trusted_runner` 会真实启动新的 Python 进程。它只执行包内已审阅的固定业务字节及固定验收器，其他 Python 源码先拒绝。它精确载入固定测试，不自动搜索目录中新加的测试；执行路径也不能被符号链接或 junction 替换。无关的普通笔记可以留下。你自己写的程序要由操作者审阅，或者交到经过验证的隔离环境；不能删除这个检查来把任意上传变成可执行代码。这仍不是能抵御其他进程并发替换文件的操作系统沙箱。

`verify` 记录整个可见源码文件集的摘要，`green_is_current` 在最终交付时再次比较。增添一个新文件也会让旧结论失效。测试只证明本次规定输入在本次字节上的结果，不证明未来所有输入。

**思路：** 先记录“测试失败”，修正后再产生一份新的验证，不覆写旧失败日志。

**定位：** 独立比较退出码、测试数、failures/errors 和前后文件摘要；不要解析一段绿色文字作为唯一依据。

## 第六站：cwd 与权限边界不是同一件事

公开检查会在它自己的临时父目录里创建 `owned-probe-outside.txt`，让一个已审阅子进程以仓库为 cwd，却修改这个外部文件。实验结束后只清理这批自建临时文件。你会看见：设置 cwd 没有阻止绝对路径写入。

`assess_probe` 读取宿主观察到的文件变化、网络计数和虚构凭据泄漏，不相信子进程自报。真实违规优先判 `unsafe`；证据缺失、旧 nonce 或没有完成标记判 `inconclusive`。有限探针通过也不等于绝对隔离。

`executor_for` 只从宿主登记表选取当前配置、未过期、已通过验证的执行器，选择时不调用。游戏目前没有登记通用不可信代码执行后端，所以保持任意上传执行关闭。这不妨碍你在本机完成自己审阅过的工程。

## 第七站：有界恢复、重启和自己做决定

Git 有工作树和暂存区。`git diff` 看尚未暂存的变化；`git diff --cached` 看将进入下次提交的暂存变化。把同一笔记改两次、只暂存第一次，亲手比较两个 diff，再预测提交会包含哪次内容。[Git diff 官方说明](https://git-scm.com/docs/git-diff.html)

本工程的恢复函数只恢复这次改动的目标文件，并要求它仍等于我们写出的版本。其他文件、暂存区、未跟踪笔记都保留。一般 Git 恢复时也要明确来源、`--worktree`/`--staged` 与具体路径；不要在真实项目里用大范围恢复命令练手。[Git restore 官方说明](https://git-scm.com/docs/git-restore)

最后实现自己的 `host.run`：保留任务和约束，接收有界决策，调用真实工具，把观察标记为不可信，批准后才改，最后再次核对当前验证。模型提前说 `final` 只能得到 `unverified`。可以用手写规划器作为决策来源，不必调用付费模型，更不需要为这个小任务引入多个 Agent。

把状态写成 JSON 后，用新的 Python 进程恢复。旧文件变了就 `needs_refresh`，约束变了就 `needs_review`；即便一切相同也要 `ready_to_reverify`，重新验证。批准不随 checkpoint 复活。

## 继续查证的第一方资料

- [Python 3.12 pathlib](https://docs.python.org/3.12/library/pathlib.html)：路径、符号链接与 Windows junction；`is_junction` 从 3.12 提供。本项目没有完成 Windows 实机 junction 验收。
- [Python 3.12 subprocess](https://docs.python.org/3.12/library/subprocess.html)：参数列表、cwd、返回码、捕获输出与超时。`cwd` 是启动目录，不是隔离承诺。
- [Python 3.12 venv](https://docs.python.org/3.12/library/venv.html)：独立解释器入口与环境；本练习不要求安装包。
- 上述 Git 两份文档解释官方命令，本练习的修补/恢复函数是自主实现。材料于 2026-11-14 核对，不把网页当前版本当作你本机已经安装的版本。
