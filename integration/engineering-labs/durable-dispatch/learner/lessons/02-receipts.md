# 02 · 没收到回话，事情可能已经做了

## 从内存去重到持久意图

用一个 `set()` 记“处理过的请求”，在同一进程中可能有效。关闭进程后集合消失，重试会再做一次。此时需要持久记录；但只保存“做过”仍不够，必须知道这个意图要求做什么、对应什么结果。

例子：同一个朋友重复询问 `request-8: 借一把伞`，应该返回原收据；如果把 `request-8` 改成 `借三把伞`，就有冲突。另一份 `request-9: 借一把伞` 可能是第二次真实借用，不能因为文字相同就当重复。

因此区分三件事：operation ID 标识业务意图；payload 是这一意图的内容；receipt 是接收方对该意图的结果凭据。本包的 receipt 是不透明非空字符串，你不能依赖它的具体前缀或解析其中数字。

## 四个时刻

一次调用经过：接收方尚未执行 → 接收方修改实际数据 → 接收方保存回执 → 调用者收到回复。网络或进程故障可能发生在任何两步之间。最容易误判的是最后一个边界：对方已提交，但回复丢了。调用者只看超时，无法断定没有发生效果。

在本包，effects 是实际虚构通知记录，receipts 是去重与查询记忆。它们在**同一个 SQLite 事务**内保存。测试会让插入 receipt 的 SQL 失败，再从另一连接查 effects，确认没有先行提交的孤立效果。

一个有用的独立 SQL 实验：在一次性表上创建触发器，让某次 INSERT 主动报错：

```sql
CREATE TRIGGER refuse_measurement BEFORE INSERT ON readings
BEGIN SELECT RAISE(ABORT, 'measurement refused'); END;
```

这不是绕开程序的假数据，而是让真正的 SQL 写入失败。不要在真实数据库上练习删除或触发器操作。

## 练习顺序

1. 实现无副作用的 `lookup`，理解未知 op 返回 None。
2. 实现一次新意图的 receive，读回一条 effect 与一份 receipt。
3. 关闭连接、换一个进程重放相同内容，保留同一 receipt。
4. 重放改过的内容，要求 ValueError，旧表不变。
5. 模拟回复在 commit 之后丢失，再重启调用者恢复。

不需要让 `receive()` 自己捕获所有错误后返回“失败”。保留真实异常，才能让调用者知道哪些信息尚不确定。

## 保证有保存期限

本练习把 receipts 作为重放记忆。如果人为删去 receipt 而保留 effects，再次 receive 会产生另一个效果；这项测试故意揭示保证的边界。真实系统必须决定回执保留多久、归档与业务效果如何关联。不能仅凭一个去重表就宣称“永远恰好一次”。

## 独立应用

自己用两次独立 Python 启动证明重放行为，并用查询结果支持结论。再为“内容相同但 ID 不同”增加测试。解释只保存请求摘要、不保存内容冲突规则会留下什么歧义。错误输入应在创建数据库前被拒绝；布尔值不能偷偷变成合法标识。
