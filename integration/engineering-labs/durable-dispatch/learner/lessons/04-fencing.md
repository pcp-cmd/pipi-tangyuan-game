# 04 · “我还在做”不能证明“我仍有资格写”

## 为什么只有工人名字不够

想象汤圆领取一个任务，约定十秒内有效。他运行很慢，十秒后另一个进程重新领取。旧进程恢复时可能仍记得“我负责这项工作”。如果最终写入只检查名字，甚至两个进程用了同一个名字，旧结果就可能覆盖新结果。

代次 generation 是每次领取时递增的号码。它和 owner、租期一起构成这次资格，但**真正写入的数据库必须自己检查它们**。先在 Python 检查一次，再无条件 UPDATE，检查与写入之间仍可能被别的进程改变。

## 先练一个不同问题

给一份编辑草稿保留 revision。编辑器读到 revision=4；提交时执行“仅当 revision 仍为 4 才改正文并把 revision 加一”的条件 UPDATE。查看 cursor.rowcount：0 表示前提不成立，不等于成功修改了零个字符。这个模式帮助你理解为什么条件必须和写入放在同一个受保护操作中。

## 本题合同

`claim` 只处理单行任务。只有 pending 且 `until <= now` 时可接手，成功增加 generation。`publish` 要求 pending、正确 owner、正确 generation 且 `now < until`。边界等号有意义：到期的那一刻已经不能发布。

时钟由调用者显式传入，测试不用靠机器睡十秒。这个可测试时钟是一种设计接口，不是假装测过真实多机时钟偏差。严格拒绝 bool、NaN、无穷大和无效 ttl，避免 True 被当 1 或比较异常偷偷放行。

两种合法思路都可以：在写事务里读取并验证状态再更新；或使用带全部前提的条件 UPDATE，并检查实际影响行数。无论选择哪种，都不能跨两个独立事务完成“资格检查”和“发布”。

## 顺序练习与并发练习

先运行单进程用例：同名再领取得到第二代；第一代发布被拒；第二代到期也被拒；完成后不能重领或覆盖。之后运行两个真实进程争同一过期任务。进程在 stdin 屏障处等候，放行后同时争抢；检查数据库实际只有一位新持有者。

再关闭所有进程，用新进程继续操作同一个数据库，确认 generation 没重置为 1。不要每次初始化都 DELETE 或 INSERT OR REPLACE 任务行。

## 独立解释

为什么“同 owner”仍会出现过期结果？为什么新工人到来不是旧资格失效的唯一条件？为什么本地 fencing 不能阻止已经发到另一个服务的请求？用自己的时间线解释，再为刚好到期和同名两代分别写测试。真实跨机器时钟、进程暂停和远端权限仍需进一步工程验证。

## Python整数与存储边界

Python int 可以比数据库INTEGER更大。本包容量明确为0到2**63-1，代次为1到2**63-1；超范围应在绑定SQL参数前按合同拒绝，不等SQLite报OverflowError，更不能先创建空库。代次用尽需显式停止，不能回绕变成旧工人的资格。请分别测试最大合法值、下一值与bool。
