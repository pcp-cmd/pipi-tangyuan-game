# 05 · 批准哪一件，就只执行哪一件

## 三种角色先分清

用户或受信宿主决定权限；模型或工具提出建议；执行层实际产生效果。建议文本里写“已获得批准”，不能变成宿主授权。单独检查某个 `approved=True` 字段，也不能证明收件人、正文、操作者与有效期就是刚才批准的内容。

本章先做一个很小的离线边界：串行内存 grant，由可信宿主创建；执行器消费一次 grant，调用本地 effect。没有身份服务器，没有并发授权数据库，也没有真实邮件。

## 用不同例子理解内容绑定

如果批准的是“把阅读提醒放进蓝色信箱”，执行时却换成红色信箱，界面上显示的同意没有保护实际效果。授权至少应绑定动作、操作者和确切参数，并检查有效期与是否消费过。

把参数转成固定 JSON 字符串，可以比较“同一内容”的一个明确表示：

```python
import json
example = {"label": "读书提醒", "box": "blue"}
encoded = json.dumps(example, sort_keys=True, allow_nan=False)
copy = json.loads(encoded)
```

这个小例子不是加密签名；它只是展示稳定编码与独立副本。生产身份认证和密钥管理是另一个问题。本题 args 的字段合同严格限制为 to/body 两个字符串。

## 可变对象的第二个陷阱

`actual = args` 只是另一个引用，执行回调改 actual 也会改原请求。你需要把经过验证的内容固定成独立快照，并确保调用 effect 的正是这份内容。只验证 A、再从别处读取 B 来执行，仍然越界。

`authorize` 验证并将 used 改为 True，成功返回 None。`execute_approved` 安排快照、验证、消费与实际 effect 调用。拒绝时 grant 和 args 都保持原样，而且 effect 调用次数必须为零。

## 出错之后还能重放吗

如果 effect 抛异常，外部效果可能已发生但回复丢了。本题按一次尝试消费授权，失败后仍 used=True，原异常继续传播。它没有把“失败”等同“没做”。需要重试时，应该结合上几章的业务意图与持久回执设计；不能无条件把 grant 重新打开。

## 检查与迁移

每个拒绝用例都用一份全新 grant：错 actor、错 action、改收件人、改正文、刚好过期、used 不是 False。一个已消费 grant 连着测十种错误，十次拒绝可能只是同一个原因，证明不了每个边界。

在自己的副本做“检查蓝色信箱，执行红色信箱”坏实现，让测试记录真实 effect 参数并拒绝它。再解释：如果两个进程同时读一个内存 grant，这个练习为什么还不够？这项限制必须保留在 DELIVERY，不能把串行例题写成生产级权限系统。
