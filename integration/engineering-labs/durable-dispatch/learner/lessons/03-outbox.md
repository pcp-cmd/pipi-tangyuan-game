# 03 · 先保存“有事要做”，再处理外部效果

## 两个数据库不是一个事务

商店保存了一份订单，还要通知仓库。如果先保存订单，再直接调用通知服务，程序可能刚存好订单就退出，之后没人知道需要通知。如果先发通知，再存订单，通知可能成功而订单失败。给本地代码加一个 try/except，不能把两个独立系统变成一个事务。

待发箱把“订单”和“这份订单需要通知”一起存入本地数据库。另一个步骤读取 pending 消息，调用接收方，再登记已确认。外部调用不在本地业务事务里：它可能慢、可能失败、可能已经产生效果。

先用与作业不同的生活例子推演：一本书登记借出，同时生成一条提醒草稿。真正送出提醒之后才收到回执。讨论这四个事实分别属于哪个系统，再阅读函数合同。

## 精确区分状态

| 发送方 | 接收方 | 能据此说什么 |
|---|---|---|
| pending | 没有 effect | 可能尚未尝试 |
| pending | 已有 effect/receipt | 对方可能已完成，但本地还没确认 |
| sent + receipt | 已有 effect/receipt | 本次实验两侧记录对得上 |

`pending` 不等于“肯定没发过”。本地拿到一个非空字符串也不能自行证明第三方诚实：本包因此用独立查询看接收方真实 effects。

## 实现任务

先实现 `enqueue` 的本地事务：orders 与 outbox 同时成功，新消息 pending/NULL。重复请求不能把已经 sent 的消息重置为 pending，也不能抹掉 receipt。遇到已有订单却缺少对应消息，应该报告不一致，不凭猜测生成一条新的“历史”。

再实现 `deliver`。它是串行练习：本轮读取的 pending 按 op 排序；每条调用 `send(op,payload)`；只有合法回执才能确认。调用 send 时释放本地数据库连接，避免等待外部结果时占用连接或写锁。失败时停止，当前项与后续项仍 pending；之前已经确认的项不回退。

`crash=True` 发生在 send 返回后、本地 ack 前。重试必须使用原来的 operation ID。若每次重试生成新 ID，接收方会认为是新的业务，反而制造重复效果。

## 真实演练

完成后按 README 的 queue → dispatch --lose-reply → inspect → 新进程 dispatch → inspect 流程走一遍。把每一步的两侧表状态写成自己的表格。再用 `--interrupt` 区分“回复丢失”和“回复已收到但本地还没记账”的故障点。

Debug：在自己的副本故意把 state='sent' 写在 send 之前。让 send 抛 OSError，观察系统是否会永远跳过这条未完成消息。写一个检查实际表的测试抓住它，再修回。不要用返回值字符串里有没有“sent”替代数据库检查。

## 何时需要下一章

这个发送器没有承诺多个发送者恰好只调用一次 send。接收方的持久去重保护本练习的效果，但多个工人同时更新其他共享资源时仍需要资格边界。下一章的代次检查保护的是实际发布点；它也不是能凭空约束所有外部服务的万能锁。
