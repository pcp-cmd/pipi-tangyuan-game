# 09 · 陌生需求：航次改期清单

完成上一章后，把讲解收起，仅使用这一份业务合同和 `reminder_plan.py` 的接口说明设计。你收到航次清单，要产生通知草稿，但没有获得批准权。数据处理、持久状态、人工批准和恢复派送现在要在一个陌生需求中配合。

这项迁移增加了批次原子性、来源快照、歧义数据与手工编辑保护；不是把“通知”改成“航次”的函数改名。它与第七章容量预约都属于同一份 `durable-dispatch` 工程，不能重复计成多个独立毕业作品。

## 输入与业务决定

查看 `examples/trip-changes.json`。时间用从起点开始的分钟数表示；本题不要求时区库。每行有航次、虚构收件人、原时间、新时间和取消标志。

- 未取消且时间没变，不生成草稿。
- 取消的航次即使时间相同也生成取消通知。
- 同一航次与收件人出现两次，整份文件不明确，拒绝整批。
- 同航次可以通知不同的人；不要只用航次编号去重。
- 布尔值不是合法分钟数。先检查完整文件，再开始保存。

精确字段、正文、稳定草稿ID和批记录结构见函数 docstring。ID 使用有明确分隔的 JSON 编码后取 SHA256，避免 `ab+c` 与 `a+bc` 拼接碰撞。该摘要用于绑定已知输入，不证明内容来自可信人。

## 要独立解决的边界

先写自己的状态表再编码：

1. 第三行格式错误，前两行是否已产生草稿？
2. 同批号、相同文件重放，已经批准或发送的草稿会不会重置？
3. 同批号换文件，怎样发现，而不是覆盖旧记录？
4. 用户已编辑一份草稿，新导入会不会替他改回旧文字？
5. 保存第二份草稿时数据库拒绝写入，是否留下半批？
6. 新批次完成后，如何证明没有自动批准、排队或发送？

你的实现必须让新草稿与批记录一起提交或一起回滚。只保证单行原子性不足以满足整批要求。文件原始字节变化视作新快照；本题选择严格保留旧批号绑定，不“猜测”两种格式是否代表相同原意。

## 真正运行，而不是填写状态

```sh
python -m durable_learning --workspace ./sailing-state plan-trips examples/trip-changes.json departure-batch-1
python -m durable_learning --workspace ./sailing-state inspect
python -m unittest tests.test_reminder_plan -v
```

前两条应显示两份草稿，没有批准、派送任务或 effect。记下其中一个实际输出的 `trip-...` ID，使用上一章的 `approve-draft` 和 `queue-approved`，只批准那一份，再用 `personal-send --lose-reply` 制造未知结果；新进程查回执恢复后，接收方仍只有那一份效果，另一份保持草稿。

不能把示例命令中的占位ID直接当真ID，也不能为了使检查好看而自动批准整个文件。公开检查会真实查询批准、任务、接收方表；在说明中写“不会发送”不足以替代行为。

随后独立制作一份新业务输入与至少三个新增用例，其中一个必须来自你曾犯过的错误。可选择取消与改期同时出现、不同收件人的同航次、批次内容变化、手工编辑与导入竞争等方向，说明为什么原公开样例未覆盖你的情况。你可以扩展 CLI 命令，但须保留原合同与旧实验数据库。
