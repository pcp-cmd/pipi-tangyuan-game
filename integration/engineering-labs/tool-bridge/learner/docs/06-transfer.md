# 陌生任务：观测站时间窗口

现在移除报价中的单价、数量和库存。观测站只提供每天 0 到 1440 分钟的时间表，你要判断新观测时段是否冲突。这个任务有区间边界、不同站点和重复身份，需要重新分析数据。

## 已教过的知识如何迁移

你已经学过验证字典、严格整数、遍历列表、纯函数、文件与 CLI。本任务继续使用这些工具，不要求日期库、时区或数据库。开始与结束时间都是同一天的分钟整数。

约定窗口是半开区间 `[start, end)`。前一个观测在 540 分钟结束，后一个在 540 分钟开始，它们不重叠。先在纸上画出两个窗口，再判断谁在谁的左边，不要把报价条件改个名字继续用。

## 独立合同

`slot_availability(schedule, request)` 接收完整时间表和一个请求。每条记录有唯一 id、station、start、end。请求只有 station、start、end。开始小于结束，开始允许 0，结束允许 1440；布尔值不是分钟。

完整时间表都要验证。即使一条非法记录属于另一个站点，也不能忽略。返回请求字段、严格布尔 `available` 和按原时间表顺序排列的 `conflict_ids`。不修改任何输入，也不做预约写入。

给 `check-slot --schedule PATH` 增加真实 CLI。它使用第一节已教过的单 JSON 输入、退出码和错误输出规则。

## 独立完成前先预测

时间表包含 north 的 `[480,540)` 与 `[570,630)`。分别预测 `[540,570)`、`[539,541)`、`[500,600)`、另一个站点的 `[500,600)`。写出冲突 ID 和理由，之后才运行检查。

运行 `python run_checks.py --group transfer`。再自己加零点、最后一分钟、完全包含、请求被包含、重复 id、未匹配站点中的非法记录。不要只换公开案例的数值。

## 排错与跨场景判断

一个旧实现使用闭区间，错误地拒绝相邻的两个观测。写出能够单独暴露这个错误的测试，并展示修复前失败、修复后通过。另一个实现只校验当前站点，把别处坏数据藏起来。给它设计另一条反例。

把一次实际 check-slot 调用包入你自己的观测记录，故意破坏结束日志。只凭日志还能证明什么？如果以后增加真正预约，重试前需要查什么？这个工程没有实现预约写入或并发抢占，不要把只读“available 为真”解释为已保留名额。

## 无分步提示的最终交付

让另一人给出一份你没见过的时间表。独立解释数据和边界，完成 CLI 调用，保留原表摘要与自己的新增测试。提交一份 `SUBMISSION.md`，说明三入口为什么复用同一业务函数，以及时间窗口为什么不是报价题换名。

第一层补救是重新画半开区间。第二层补救是找出“不重叠”的两个方向，再取反。需要第三层帮助时回看基础条件与列表课程，记录实际帮助，不把带解答完成的练习升级为独立证明。
