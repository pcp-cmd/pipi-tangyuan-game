# 把同一个能力放到回环 HTTP

完成本节后，你能通过真实网络连接调用报价，并判断错误发生在哪一层。服务只绑定 `127.0.0.1`，不发布到公网。

## 先运行温度的回环小例

运行 `python examples/temperature_http.py`。它沿用上一节的温度函数，在一个独立服务线程中启动真正的回环 HTTP 端点。客户端实际发送数字温度与错误文字两次请求，分别得到 200 与 400。输出里的 server_thread_closed 与 socket_closed 来自线程状态和套接字文件描述符检查，两条路径都真实关闭。

打开例子看 `Handler(BaseHTTPRequestHandler)`。继承表示沿用标准库的 HTTP 解析，`do_POST` 定义收到 POST 后的处理。`self.headers` 取请求头，`self.rfile` 读请求字节；`send_response` 与 `send_header` 写状态和头，`end_headers` 后才向 `self.wfile` 写正文。这个温度端点没有完成报价任务的路径、状态码与全部响应合同，先观察这些 API，再独立完成后面的工作。

## 一个请求有多层结果

连接拒绝意味着客户端没有建立可用连接。收到 HTTP 503 意味着对方确实回答了一个服务错误。HTTP 200 的正文仍可能是坏 JSON；合法 JSON 仍可能含错误字段。

先写下四类失败的区别，再看合同的异常类型。不要把 `except Exception: return {}` 当作容错，因为空字典会抹掉诊断信息。

标准库的 `urllib.error.HTTPError` 继承 `URLError`。因此先捕获 HTTPError，再捕获连接错误。反过来会把实际状态码吞入连接错误分支。取得响应后用上下文管理器关闭它。

## 观察一个异题的状态与正文

下面是人的判断练习，暂时不用写服务器。

| 观察 | 能得出的结论 | 还不能得出的结论 |
| --- | --- | --- |
| 天气端口连接拒绝 | 本次没有取得响应 | 城市没有天气数据 |
| 503 与 `{"error":"busy"}` | 对方报告繁忙 | 重试必定安全或会成功 |
| 200 与 `{` | 收到了无效 JSON 正文 | 温度为零 |
| 200 与 `{"temperature":"hot"}` | JSON 语法有效 | 温度满足数字合同 |

给天气结果增加必填 `unit`，预测缺少单位时应在哪层拒绝。不能擅自把缺少单位理解为摄氏度。

## 搭建真实端点

`ThreadingHTTPServer(("127.0.0.1", 0), Handler)` 让操作系统分配空闲端口。通过 `server.server_port` 得到实际端口。启动命令必须只在服务已创建后输出 ready JSON。绑定失败不能先报 ready。

为 `POST /quote` 实现 Handler，检查 Content-Type、Content-Length、UTF-8 和 JSON，然后调用已经完成的 `quote`。正常返回一个 JSON 对象。HTTP 层不再实现第二份库存算法。

限制正文为 32768 字节，限制读取等待。错误方法、未知路径、坏 JSON、业务错误分别有状态码。不要用无限的 `read()` 等待一个永不结束的客户端。最后用 `server_close` 关闭端口。

客户端先确认 URL 是明确的 `http://127.0.0.1` 地址。拒绝自动跳转，避免受控回环端点把连接引向另一地址。本练习不声称回环接口天然拥有身份认证或适合处理不可信多用户流量。

## 逐步检查

先让一次合法请求返回与 CLI 相同的报价。再加坏 JSON、未知商品和布尔数量。最后运行公开的本地 HTTP 夹具，它分别返回 503、坏 JSON、错误业务字段和跳转。

`fetch_quote` 必须校验响应里的 SKU 与数量仍属于当前请求。收到另一请求的合法报价也不能算成功。测试实际关闭服务后，再次请求必须得到连接层错误。

## 分层提示与独立应用

若所有错误都成了 `TransportError`，先检查异常继承顺序。若 200 永远成功，检查 JSON 解码后是否还有响应合同检查。若测试偶发挂起，检查请求正文长度、子进程 stderr 排空和关闭等待。

自己加一个“合法 JSON 但属于另一 SKU”的 HTTP 夹具，以及一个大于长度限制的正文案例。证明 CLI 与 HTTP 没有修改原目录。说明为什么本例没有自动重试：网络错误不能单独证明服务端没执行过，只读报价也不能替你证明未来写操作的重试安全性。
