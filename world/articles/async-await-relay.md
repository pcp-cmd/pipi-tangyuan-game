# 先等回执，再启航：请求不等于结果

皮皮发出取件请求，汤圆负责交付。汤圆手里需要的是包裹本身，不是“取件申请单”；交付完成之后，码头要的又是实际回执，不能把“已经开始交付”当成成功。异步程序里，这几件事都有不同的对象和时间。

开始前，先能区分函数与调用结果，会用参数传值，也知道普通异常怎样向调用者传播。“组合工序”的顺序调用经验仍然有用，只是这里每一步可能要等待外部许可。

## 调用 async def 得到了什么

调用 `async def` 函数，得到协程对象。仅仅创建它，不会自动执行完函数体。`await` 表达等待它的完成结果；遇到尚未完成的等待，当前操作暂停，事件循环可以推进其他已准备好的任务。

先看一个只有一步的例子。这里没有交付函数，目的是看清“得到待办操作”和“得到结果”的区别。

```python
import asyncio

async def main():
    events = []
    parcel = []

    async def receive():
        events.append("实际取件")
        return parcel

    operation = receive()
    print(events)
    value = await operation
    print(events)
    print(value is parcel)

    receipt = asyncio.get_running_loop().create_future()
    receipt.set_result(0)
    print(await receipt)

asyncio.run(main())
```

输出依次是 `[]`、`['实际取件']`、`True`、`0`。空列表包裹保持原对象，回执零也仍是结果。最后的 `Future` 表示一个结果将被设置的可等待对象；这个例子已经设置好了，所以等待能立即得到零。

协程只是可等待对象的一种。`Future` 和实现 `__await__` 协议的对象也可以等待。本课接收的函数承诺返回可等待对象，没有把输入缩窄为协程。`asyncio.create_task` 在这里使用的 Python 3.12 接口接收协程，不能不加区分地替代对任意可等待对象的 `await`。

独立脚本最外层可以用 `asyncio.run(main())` 启动事件循环；游戏已经在它的异步执行范围内，工作函数应使用 `await`，不要在里面再次启动同一线程的事件循环。等待也不会让普通耗时计算自动跑到另一个 CPU 核心，阻塞代码仍可能挡住其他任务。

## 交接的两端都必须等到完成

本课入口 `relay(fetch, publish)` 实际开始后，调用并等待无参 `fetch()` 一次。取件完成以后，才能把得到的同一对象交给 `publish(value)`，并等待交付一次。最后返回的是交付回执本身。

这就能解释两个具体错误。写 `publish(fetch())`，对于返回协程的取件函数，交过去的是尚未等待的操作对象；返回 `publish(value)`，又只是把交付操作交了出去，没有证明交付完成。还有一种是返回 `True` 作为“已提交”标记：它丢掉真实回执，也无法表达交付随后失败。

取件结果可能为 `False`、`0`、`None` 或空容器，合同依然要求交给交付函数，不能写成“值为真才发布”。用一个预先创建的可变对象检查 `is`，能够发现不必要的复制或格式转换。

取件失败，交付零次；交付失败，不能伪造成功。普通业务错误保留原对象向外传播。一次取消沿等待关系传播，已开始操作若在 `finally` 中异步收尾，要遵守正常等待语义，不能为提前返回留下自己启动的后台任务。取消的请求与终态将在后面的停船课专门展开。

这里把 `StopIteration`、`StopAsyncIteration` 留给迭代协议终止使用；输入函数用普通业务错误报告失败。在协程或生成器边界非法漏出的终止信号可能被转换，不在错误身份保证范围内。

## 用许可来观察，而不是猜秒数

测试时让取件先停在一道许可前，确认交付还未调用；放行取件后，让交付又停在另一道许可前，确认整项接力还未返回。最后发出交付许可，才应该得到真实回执。下一课会用 `Event` 表达这些许可。等待固定时间只能当防挂死的限制，不能证明哪一步先发生。
