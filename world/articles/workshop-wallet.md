# 拒绝付款的决定，要由钱包自己守住

皮皮有10金币，先花3，再试花8，最后花7。中间一次买不起，余额应停在7，最后一次才能刚好付清。若先扣钱再判断，失败支付已经使后续故事走向另一条路。

你已学过类和函数组合。类描述一类对象能保存什么状态、提供什么操作；每次调用类创建一个实例。方法中的self指向这次被操作的实例。钱包自己的pay方法必须守住规则，不能只在外层故事函数里检查，因为调用者也能直接调用wallet.pay。

## 两个实例，两个状态位置

下面在普通Python中建立简单计步器，观察状态归属，不实现钱包扣款。

```python
class Counter:
    def __init__(self, value):
        self.value = value

    def advance(self):
        self.value += 1

first = Counter(2)
second = Counter(9)
first.advance()
print(first.value, second.value)
```

输出 `3 9`。`__init__` 在创建对象时把起始值放进各自的self.value。调用first.advance时，self是first，更新不会碰second。不要用一个共享全局余额代表所有钱包；那会让新钱包覆盖旧钱包的状态。

本课在模块顶层定义Wallet，外部才能直接创建 `Wallet(balance)`。实例的balance可读。pay接收整数cost：先判金额非负与余额足够，再决定是否扣除；成功返回真正的True，失败返回False且余额不变。不要用“扣后余额”作为返回值，因为成功付清会得到0，它在条件里反而像失败。

## 按时间画出余额，再写故事函数

从10出发，付款3后余额7、结果True；付款8失败，余额仍7、结果False；付款7后余额0、结果True。`wallet_story` 应创建一个钱包，再按costs的输入顺序调用它，收集每一次布尔结果，最后返回余额和结果列表。

顺序不能重排。先付7再付3，虽然某些总额相同，成功记录的含义可能不同。负金额必须拒绝，否则减去负数会给钱包充值。0金额合法，即使余额也是0也支付成功且不改变余额。空付款清单则保持起始余额，结果列表为空。

测试不仅要看wallet_story的输出，还要直接创建两个Wallet交替调用pay。让其中一个发生失败与负金额支付，确认另一个完全没变。若故事输出正确但直接调用能透支，说明业务限制藏错了层。

## 加入预留款，而不提前消费

另设计带预留的票夹。reserve(amount)占用可用余额但不算已消费；confirm(token)才完成扣款，cancel(token)释放预留。每个预留标识只能确认或取消一次，不同票夹互不影响。

先写状态表，再用“预留两笔、取消一笔、确认另一笔、重复确认”核对余额、可用额和标识状态。这里从一次付款变成多阶段状态转换，单个True/False列表不足以解释责任。保留事件与状态记录供人工评估；本课通过不自动证明你完成这份独立设计。
