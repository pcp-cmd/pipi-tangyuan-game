# 把失败也变成契约：收到坏订单后，调用者该看什么

汤圆从留言板收订单，约定写成“名字:数量”。有人漏写数量，有人多写一个冒号。对于这些可预期的输入问题，界面需要稳定地显示“格式有误”，不该被一次整数转换错误直接打断；但代码自己的缺陷也不应被偷偷伪装成坏订单。

你需要会拆分字符串、字典返回值、条件判断和捕获特定异常。这里的成功与失败都会返回字典，调用者先检查 `ok`，再按对应结构取内容。这样不需要猜“空字符串是不是失败”，也不用从错误文案里提取含义。

## 拆分和转换各自负责一件事

名字和数量之间必须恰好一个冒号，得到恰好两段。`"鱼:2:3"` 不能只取前两段当作合法；忽略剩余字段会掩盖输入错误。名字去首尾空白后必须非空，但内部空白、大小写和 Unicode 字符要保留。`" Fish  Roe :4"` 的商品名应保留为 `"Fish  Roe"`。

数量按 Python 的 `int` 转换规则读取，然后要求大于零。这个要求和“只能包含 ASCII 数字字符”并不相同。先实际观察几份数量文本：

```python
for raw in [" +2 ", "1_0", "１２", "2.5", "²"]:
    try:
        value = int(raw)
    except ValueError:
        print(repr(raw), "不能转为整数")
    else:
        print(repr(raw), value)
```

前三个能得到 2、10、12；小数文本和上标二不能这样转换。合法的符号、数字分隔符和 Unicode 十进制数字由 `int` 的规则决定。先加一个自己写的 `isdigit()` 筛选，可能反而把合同接受的 `+2` 拒绝，又把某些不能转成整数的字符误认为可用。

整数转换成功只是得到一个整数，`0` 与负数还要被业务规则拒绝。不要把“能解析”直接当成“能下单”。

## 固定结果形状，让调用者能继续

`parse_order(text)` 成功时返回 `{"ok": True, "item": 清理后的名字, "quantity": 整数}`。格式或数据错误统一返回 `{"ok": False, "error": "invalid"}`。字段名、布尔值和错误标记都是双方约定的一部分；不要有时返回 `None`，有时返回错误字符串。

可预期的拆分／转换问题可以转为这个失败结果，而程序缺陷应该继续暴露。假设你把变量 `quantity` 拼错，发生 `NameError`；若用覆盖整个函数的 `except Exception` 都返回 `invalid`，所有合法订单也会被界面当成输入错，修复时失去真正原因。捕获范围要贴着可能失败的输入操作，捕获类型也要和预期失败相符。

这课输入约定是文本，没有要求你为任意对象设计全套容错；也不是通用 CSV 解析器。若商品名需要包含冒号，得先另定转义或编码格式，不能靠悄悄丢掉段落解决。

检验时按不同失败原因准备例子：没有分隔符、多一个分隔符、空白名字、不能转换的数量、能转换但非正的数量。再保留两个容易被“过度修正”的成功例子：含内部双空格的名字、带正号或 Unicode 数字的数量。只验证“鱼:2”不足以说明你遵守了输入边界。

## 独立任务：一批记录里保留每一行的去向

设计批量导入函数，输入多行文本，每个非空行是“名字:数量”。空白行跳过，但占物理行号；合法行按出现顺序进入成功列表，坏行以原物理行号进入错误列表。一个坏行不能阻止后面的合法行被解析。函数只整理数据，不向外写文件或扣库存。

先决定返回结构，再用“合法、空白、坏行、合法”四行验证两个列表和行号。说明哪些部分可以复用单行解析，哪些必须由批量层负责；还要注入一个真正的程序错误，确认它不会被当成某一行的普通失败。新增的错误汇总与继续策略需要你自己的运行记录和人工复核，当前课程只检查单行合同。
