# 三个泊位的救援队

码头有三个泊位，九艘船等待维修。一艘船正在等零件时，另一个泊位仍能接船。但如果先给九艘船都创建维修任务，再让其中六艘等待空位，程序仍然保存了九份任务。船越来越多，等待的任务也会越积越多。

这次你要写的调度函数负责控制两件事。它只让有限数量的工作处于未完成状态，也只在有空位时向输入索取下一项。它还必须对自己的任务负责。一个任务失败后，函数不能已经向调用者报错，却把其他任务的收尾留在后台。

工作台入口是 `async def map_bounded(items, limit, worker)`。`items` 是有限的同步可迭代对象，可能只能读一次。`limit` 是正整数，不能是 `True` 或 `False`。`worker(item)` 为一个输入提供可等待的工作。成功时，函数交回一个列表，结果顺序与输入顺序相同。

## 先确认你能追踪等待与收尾

前面的“先等回执，再启航”解释了 `await`，“亮着的信号，不是一箱货”解释了 `Event`，“请停船，也等绳索收好”解释了请求取消之后仍要等待目标结束。如果你还不能说出这几个动作的区别，先回到对应课程。路线建议先学“不会偷偷续流的灯塔”，它还要求你分清资源是谁借来的、由谁关闭。

调用一个 `async def` 函数，会得到协程对象，函数体不会因此立刻全部执行。`await` 等待可等待对象的结果。`asyncio.create_task` 把协程交给事件循环调度，当前协程之后可以做别的事，再等待这个任务。

本例使用 Python 3.12 的默认任务调度，没有安装会立即执行协程的任务工厂。多个任务在等待时交替推进，叫并发。这不保证 Python 代码在多个 CPU 核心上同时计算，也不保证任务轮流获得同样多的时间。长时间不让出执行权的计算，会挡住同一事件循环中的其他任务。

下面先观察一件更小的事。等待许可的工人被取消后，仍要完成 `finally` 里的收尾。这个例子用于原生 Python 3.12 独立文件，不要把末尾的 `asyncio.run` 复制到游戏任务函数内。

```python
import asyncio

async def main():
    entered = asyncio.Event()
    closing = asyncio.Event()
    allow_close = asyncio.Event()
    events = []

    async def worker():
        try:
            entered.set()
            await asyncio.Event().wait()
        finally:
            events.append("开始收尾")
            closing.set()
            await allow_close.wait()
            events.append("收尾结束")

    task = asyncio.create_task(worker())
    await entered.wait()
    task.cancel()
    await closing.wait()
    print(task.done())
    allow_close.set()
    try:
        await task
    except asyncio.CancelledError:
        print("调用者收到取消")
    print(events)

asyncio.run(main())
```

第一行输出是 `False`。此时工人已经开始收尾，任务仍未结束。允许收尾后，调用者才收到取消，最后一行是 `['开始收尾', '收尾结束']`。

这里的顺序由三个 `Event` 决定。没有“等一秒应该够了”的猜测。把 `await task` 删除，只保留 `cancel()`，就失去了“离开前已经收完”的保证。本课要求调度函数把这个保证扩展到它拥有的全部子任务。

## 空位、读取和结果是三种不同的状态

假设上限为 3，编号为 0、1、2 的工作都在等待。调度函数此时不能读取编号 3 的输入，也不能先把剩余输入变成列表。输入可能来自逐项产生数据的对象，读取本身就可能有成本或触发异常。

某项工作结束后才有空位，调度函数可以继续取一项。正常完成时，每个输入恰好调用一次 `worker`。失败或取消后，尚未开始的输入不必处理，已经开始的工作也不能偷偷重试。

完成顺序与交付顺序独立。若编号 2 先结束，编号 0 最后结束，返回列表仍按 0、1、2 排列。给输入分配编号后，再记录这个编号对应的结果，就能保留这两个顺序的区别。

```python
results = [None, None, None]
completed = [(2, "桅杆"), (0, "船底"), (1, "灯具")]
for index, value in completed:
    results[index] = value
print(results)
```

输出是 `['船底', '灯具', '桅杆']`。这个小例只说明放置结果的位置，不会创建并发任务。

在完整实现中，`None`、`False`、`0` 和空字符串都可以是正确结果。不能用结果的真假判断任务有没有完成，也不能把“尚未写入的槽位”与“任务返回了 None”混为一谈。结果还必须保留原对象，不要为了统一格式把它们转换成字符串或复制成另一个对象。

## 任务组能管到哪里

`async with asyncio.TaskGroup() as group:` 建立一段拥有子任务的范围。在范围内，`group.create_task(coroutine)` 登记子任务。离开这个范围时，任务组会等待它拥有的任务结束。普通子任务失败时，它会请求其他子任务取消，等待收尾，再把错误交出来。

任务组没有自动提供并发上限。你在里面创建一百万个任务，它仍会登记一百万个。`Semaphore` 可以限制同时进入某段代码的数量，但“先创建全部任务，再等待信号量”依然会消费全部输入并创建全部任务对象，不符合本课的需求。

可以考虑固定数量的消费任务，也可以维护一个只装有限数量任务的集合。前者在一个工作结束后取下一项，后者在一个任务结束后补位。无论哪一种，都要把“取到输入、确定编号”和后面的等待分清，保证没有两个工作错误地使用同一个结果位置。

还有一个接口细节。`worker(item)` 的合同是返回可等待对象，不保证每次都返回协程。它也可以返回 `Future` 或自定义可等待对象。`create_task` 接收协程，不能把任意可等待对象不加处理地传给它。你的调度逻辑需要真正 `await` 工作返回的对象。

## 不同的退出原因，需要各自交代清楚

先检查 `limit`。非法值要抛 `ValueError`，而且不能先调用 `iter(items)` 或 `worker`。`bool` 是 Python 整数类型的一种子类，因此宽泛的整数判断还不足以排除 `True`。本课要求的是严格正整数。

通过上限检查后，再取得迭代器。若最初的 `iter(items)` 就失败，传播同一个异常对象。此时还没有开始工作，不必把它包装成一个多任务失败。

开始工作之后，读取下一项、调用 `worker` 或等待工作结果都可能失败。对普通异常，停止继续取得新输入，请求其余已启动工作取消，并等待全部收尾。最后用异常组交出实际错误。异常组把多个错误放在同一份结果中，兄弟任务清理时再次抛错，也不能覆盖原来的工作错误。检查会核对组里原始异常对象的身份，不要求你制造固定的嵌套外形。

如果调用者取消整个映射，调度函数要取消自己的子任务，等它们收尾后再传播 `CancelledError`。这个异常继承自 `BaseException`，常见的 `except Exception` 不会捕获它。需要清理时通常应依靠 `finally`，并保留取消的传播。

子任务也可能自己取消，输入的 `next` 也可能发出 `CancelledError`。这两条路径不能伪装成成功的 `None` 或 `[]`。在没有额外清理错误时，调用者最终应收到 `CancelledError`，全部已启动工作都已结束。

这正是直接套用 `TaskGroup` 容易遗漏的地方。任务组把某个子任务的正常取消视为一种结束，不会仅因为这个取消就按普通错误取消其他子任务。你必须把本课要求的“整项映射取消”表达出来。若方案使用 `current_task().cancelling()`，这个数表示尚未撤销的取消请求数量，不表示当前任务已经结束。以前捕获过的取消请求还可能留在计数中，不能把旧计数当作本轮的新取消。这个低层接口主要供 asyncio 内部使用，别为了清掉数字而随意调用 `uncancel()`。本课只要求已列出的取消路径，不承诺 Python 3.13 对同时发生的内外取消和取消计数的改进已经适用于这里的 Python 3.12。

`items` 是调用者借给你的。函数拥有自己创建的任务，不拥有输入对象的关闭权。成功、失败和取消都不能擅自调用输入的 `close()`。这与上一课“取得资源后负责关闭”的合同不同，决定行为的是所有权约定，不能看到 `close` 就调用。

## 在闸门还关着时检查

实现后，先准备三个能等待事件的工作，让它们都进入等待。此时检查输入恰好读到三项，第四项还没取出。若一个工作都不能与另一个同时等待，程序可能仍是串行。

再按 2、1、0 的顺序放行，核对完成顺序与返回顺序。最后故意让一个工作失败，让另一个工作停在清理闸门。只要清理闸门还关着，整个映射就不能先结束。放行清理后，再检查错误与所有子任务的终态。

游戏的真实验收还包括空输入、上限为 1、工作自己取消、输入取消、最初取得迭代器失败，以及工作和清理同时失败。每一种失败都在检查一个可观察的承诺。通过正常路径不能替代失败路径。

本课不承诺强制终止拒绝响应取消的协程、线程或进程。清理永远卡住、清理期间反复取消的全部竞态，也不在本课合同内。已经写出的业务效果不会随着取消自动撤销。返回完整列表还需要保留全部结果，因此这里解决的是有限输入的映射，不是无限数据流的常量内存处理。

## 把泊位换成一个会关闭的队列

下一次任务改为一个生产者和多个消费者。生产者逐项生成传感器记录，放入容量为 2 的 `asyncio.Queue`。消费者把读数写入一个内存结果表。生产结束后，全部消费者应退出；一个消费者失败时，生产者停止继续投放，所有已启动任务完成收尾。

本题以 Python 3.12 为准，关闭协议要由你设计，不能依赖后来版本新增的队列关闭接口。先为自己的方案写关闭规则，再写代码。你要决定正常结束怎样通知消费者，失败时队列中尚未处理的数据怎样处置，每次成功 `get()` 后由谁恰好调用一次 `task_done()`。没有成功取出的项不能凭空登记完成。调用 `join()` 时，等待的是所有已登记队列项目的完成计数，不是“所有消费者都退出”这件事。

这道题改变了输入交接、关闭信号和结束条件，不能只把本课的返回列表改个顺序。先做两个消费者、五项数据的小实验，用事件让一个消费者在队列仍有积压时失败。保存失败位置、实际取出的项、清理顺序与最终任务状态。再把故障移到生产者，重新解释关闭责任。

自行核对的证据至少包含正常关闭、积压时失败、取消时收尾，以及一次刻意漏掉 `task_done()` 后确实被你的检查发现的反例。超时只能作为防挂死的看门狗，不能用某个固定睡眠时长证明事件先后。

迁移题在原生 Python 中完成，没有自动接入本课成绩。你能独立解释关闭规则并在陌生故障位置复做，才是比这次课堂通过更强的能力证据。代码、帮助来源和延时再做的结果应分别保留。
