# 被拒绝的事件，不能进入下一步状态

出航账本起始3金币，依次出现-4、+2、-5。第一笔会透支，拒绝后余额仍为3；第二笔变5；第三笔刚好变0。因此重放的结果不能靠把所有增量直接求和得到，接受与否取决于当时的余额。

事件是“要改变多少”，状态是“目前还有多少”。重放就是按原顺序重新解释这些事件，让每一步都得到相同决定。本课接收整数增量列表，只有候选新余额不为负才接受，最后返回余额与被拒绝事件的原始索引列表。

## 把候选值与已接受状态分开

在普通Python中只试算一笔货架变动，看看拒绝为何不需要撤销。

```python
stored = 2
change = -5
proposed = stored + change
print(proposed)
print(stored)
print(proposed >= 0)
```

输出-3、2、False。算出proposed并没有改stored。若条件不满足，可以直接保持旧状态；若先修改stored再检查，就必须正确恢复，而恢复操作本身又增加出错机会。

本课循环中每个事件都需要原位置。`enumerate` 能在遍历值时同时给出从0开始的索引。拒绝时记录这个索引，不记录增量值，因为两个相同的-4可能发生在不同余额下，一次被拒绝、另一次被接受。

## 零事件也是真正的事件

从0开始，事件0、-1、+2中，0被接受但余额不变，-1被拒绝且索引为1，+2最终使余额变2。若用 `if proposed` 判断可接受，会把新余额0错当失败。条件讨论的是非负，而不是Python的真假。

不要把所有负数预先删掉：余额足够时负增量应被接受；也不要把事件按正负排序，先加钱可能让原本应该失败的支出变成功。空事件列表保持起始余额，被拒绝列表为空。

调试时给每一轮写下索引、旧余额、增量、候选余额、决定、下一余额。发生差异时找第一处不同，而不是只比较最后结果。有些错误互相抵消，最终余额一样，却拒绝了不同的事件；因此两份输出都必须核对。

这里的重放只更新本地数字，不重新执行真实转账。若事件来自外部服务，重复播放是否重复扣钱还需要独立身份与去重规则，当前函数没有这个能力。

## 从一份余额重放到两份库存

另写双仓移动记录重放器，每个事件包含来源仓、目标仓与数量。只有来源足够、数量非负且仓名有效时才同时减来源加目标，否则两仓都不变。返回最终两仓数量，以及每次拒绝的索引和原因。

用一笔不足、一笔0数量、一笔从A移到B后再从B移回A的序列核对总量守恒。先定义同仓移动的行为，再测试它。新题增加两个状态的共同提交与失败原因，原先单个数的判断不能直接复制。保存逐事件预测作人工验收，不自动登记成绩。
