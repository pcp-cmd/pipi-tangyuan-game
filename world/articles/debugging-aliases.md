# 相同内容可以是三份，也可以其实只有一份

皮皮在自己的清单末尾加雨衣，汤圆的清单也多了雨衣。起始程序给每个名字都赋了items，看起来每只猫都有一份列表，实际上只是多个字典条目指向同一个对象。

先在工作台用两只猫复现一次：拿到结果后只修改其中一份，再打印另一份和原items。只比较创建时的内容相等，永远看不出它们是否会串改。这次调试要让隐藏的引用关系通过一次修改变得可见。

## 复制外层，仍没有触及共享的位置

下面的普通Python反例保留了同一种错误关系。

```python
items = ["water"]
packs = {"pipi": items, "tang": items}
copy_of_packs = packs.copy()
copy_of_packs["pipi"].append("coat")
print(packs["tang"])
print(items)
print(packs["pipi"] is packs["tang"])
```

输出两次 `['water', 'coat']`，再是True。新增外层copy不会复制值指向的列表；实际被append的那一层仍共享。应该在哪一层创建新对象，由未来要在哪一层修改决定。

本课 `make_packs(names, items)` 要给每个名字一份独立物品列表。names里的字符串互不重复。创建新列表的动作必须对每个名字分别发生：若在循环外只复制一次，再把那一份给所有名字，各猫之间仍然共享，只是原items暂时被隔离了。

## 三只猫能拆穿只修了一半的代码

不要只改第一只猫来验证。用三只猫，每次重新创建结果，分别修改第一、第二、第三份，确认其余份和原items都保持原值。一种错误实现只为第一份新建列表、后面共用一份，在两猫的浅测试里可能不容易暴露。

空items也需要每只猫各自一份空列表，不能因为内容都空就复用。空names返回空字典，而且不能顺手清空items。再次调用函数也应得到新的独立结果，不能从全局缓存拿上次被改过的清单。

本课独立性的检查针对物品列表容器。若items里面还有可变的嵌套物品，浅复制会共享那些内部对象；当前题目没有要求递归复制任意物品图。不要把“各清单append互不影响”说成“任何深层修改都隔离”，也不要未经要求复制本来需要共享的业务对象。
