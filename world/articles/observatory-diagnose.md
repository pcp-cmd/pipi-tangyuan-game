# 失败类型不同，下一步动作也不同

网络没等到响应，可以考虑重试；服务说频率过高并给了有效等待时间，应先等；权限不足则需要请求授权。把所有错误都叫“再试一次”，既无法修好权限，也会让限流更严重。

本课 `classify(error)` 只返回一个建议名字，不实际等待、不重试、不请求权限。输入是字典，kind可能缺失，retry_after可选。输出规则由题目给定：timeout对应retry，permission对应ask，rate_limit只有正整数等待时间时对应wait，其他都inspect。

## 看见一个值，还要确认它是什么

下面在普通Python中观察几种看起来像等待时间的值。

```python
for value in (3, True, 1.0, "3", 0):
    strict_integer = type(value) is int
    positive = strict_integer and value > 0
    print(type(value).__name__, positive)
```

输出 `int True`、`bool False`、`float False`、`str False`、`int False`。`and` 从左向右判断，左侧为假时不继续比较，因此字符串不会被拿去与0做大小比较。这里的严格整数检查排除了bool，不能用简单isinstance替代。

先按kind区分失败，再只为rate_limit检查retry_after。timeout不需要等待字段才被识别；permission也不应因为恰好带一个整数时间就改成wait。字段值有效与错误种类匹配是两个条件，顺序错误会串到别的分支。

## 没有足够信息时保留检查入口

`{'kind':'rate_limit','retry_after':0}` 不能表示正等待时间，负数、True、1.0、字符串'3'和None也都进入inspect。缺kind或未知kind同样如此。不要擅自把'3'转成3：题目要求判断输入是否已提供可信的类型，不要求替上游猜格式。

使用字典get可以读取可选字段而不因缺键直接报KeyError，但默认值的选择不应把缺失伪装成有效等待。比如默认1会让没有retry_after的限流错误看似已有确定建议。

用一组只改kind、另一组只改retry_after的输入检查分支。若某条总进错误路径，先看决定动作依赖了哪些字段，而不是堆更多嵌套if。当前分类只是一个有限规则表，不保证真实网络操作可以安全重试；重试是否重复产生效果还要由操作协议决定。

## 建一份有预算的处理计划

另写计划函数，输入错误字典、已尝试次数和最大尝试次数。可以重试或等待的错误在预算耗尽时必须改为停止，并保留原因；权限错误始终要求授权。返回动作、可选等待秒数及理由，不执行动作。

检查预算为0、刚好用尽、仍有一次、未知错误与坏等待时间。解释为什么增加预算不是在旧结果后面随便加个字段，而是会改变分支决策。计划的正确性需人工按状态组合核对，本课不自动记录这份迁移结果。
