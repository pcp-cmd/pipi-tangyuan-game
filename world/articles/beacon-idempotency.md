# 别把同一箱货付两次

付款请求已经发出，回执却在断线中丢了。皮皮不知道该重试还是停下。若每次重试都生成一个新编号，接收方无法辨认两次请求原来是同一件事；若只认编号不比内容，别人又可能把同一个编号拿来付另一箱货。

本课实现 `decide_receipt(receipts, key, payload)`。编号不存在，返回new；编号存在且已保存内容与本次相同，返回replay；编号存在但内容不同，返回conflict。三种判断都不修改receipts，也不进行支付。

## 存在性和内容不能合并判断

字典中的值可能为空，但键仍然存在。先观察这个小账本。

```python
receipts = {"old": {}}
print("old" in receipts)
print(bool(receipts["old"]))
print("new" in receipts)
```

输出为True、False、False。第一张收据保存了空字典，不代表没有这张收据。因此不能用 `if receipts.get(key)` 判断是否处理过，要先区分缺键，再讨论值。

只有缺键才是new。返回new也不能顺便把本次内容写进去，因为调用者此时只是询问，实际效果尚未发生。返回replay或conflict同样保持原账本，不能用新请求覆盖发生冲突的旧内容。

## 相同编号，还要核对同一意图

两个payload是普通JSON内容。对象中的键顺序不改变业务内容，例如qty和item交换书写顺序仍可能是同一请求；值的类型不能随意合并。qty为整数1和qty为True在本课是冲突，不能直接依赖Python对1与True的宽松相等。

可以先观察稳定编码后的JSON，再决定自己的比较方式。这里只处理本课给定的数据范围，不能把任意对象的字符串表示当成通用业务身份。列表顺序若不同，通常也是请求内容不同，不应擅自排序后视为同一件事。

去重课只问“这个编号见过没有”，这里额外问“见过的是否还是同一份请求”。编号相同而内容变了，应让调用者看到conflict，不能冒认旧回执证明新意图已经完成。

## 内存判断没有解决崩溃与并发

两份进程都可能同时看到new，然后各自执行一次；程序也可能完成效果后，在保存回执前崩溃。这个纯检查函数没有能力消除这些空隙。

可靠派送工程把意图、持久回执和恢复拆开观察，并要求未知结果先查回执。它仍明确使用本地虚构接收方，不能把本课的内存表理解成真实银行的一次支付保证。

调试本题时分别保留三个调用前后的账本副本。用缺键、已有空payload、完全相同内容、不同数量、不同JSON类型与键顺序变化检查结果，确认没有一条判断路径偷偷写账本。

## 让重复请求带着版本

新任务处理同一维修单的多个版本。编号与版本号一起标识一次提交，相同编号的新版本是新请求；同编号同版本但内容不同是冲突；旧版本重试要返回当时保存的原回执，而不是最新版本的回执。

自己设计存储结构，先画出编号A的版本1、版本2以及版本1再次到达时的查找过程。再测试两个编号同时使用版本1、回执为0以及冲突时账本不变。

这项迁移新增版本与结果恢复，不能只改原函数的三个状态名。它需要人工核对实际状态和原对象返回，不会自动登记为本课或工程的通过。
