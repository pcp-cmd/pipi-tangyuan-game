# 借来的三把钥匙：最后借到的，最先归还

涨潮前，皮皮依次借电源、闸门和记录器。闸门要靠电源工作，所以收工时应该先停记录器、再关闸门、最后断电。若第二台设备刚启动一半就失败，记录器根本不该再借；那台半开的闸门也不能被忘掉。

先完成单资源的“闸门钥匙”，能解释 `with`、`try/finally` 和异常对象身份。这里再增加一个前置区别：`Exception` 包含通常的业务错误，`KeyboardInterrupt` 等控制信号则直接属于 `BaseException`。清理要处理控制信号经过的路径，却不能借清理之名把信号吞掉。

## 把所有权写在取得那一刻

`managed_resources(factories)` 返回同步上下文管理器。工厂集合有限，可能只允许遍历一次。创建管理器时不能消费它；真正进入 `with` 才依次取得工厂、调用工厂、打开资源。

本题明确规定：工厂一返回对象，本范围就拥有它；即使随后 `open()` 部分失败，也要关闭。也就是说，记录归还责任的时刻早于打开成功。如果先打开再登记，恰恰最需要清理的半开设备会掉出名单。工厂直接失败时尚无新对象，不应凭空关一台设备。

全部打开成功，才进入业务块，并把按取得顺序组成的元组交给它。元组里的对象就是原资源，不能复制成替身。空工厂集合也应进入业务块，交出空元组。每个工厂本题都返回不同资源实例，范围外也不会同时关闭它们；共享同一实例的多方所有权需要另一套约定。

## 为什么用逆序

后取得的资源常依赖先取得的资源。逆序释放能让依赖者先退出，再释放它所依赖的基础设施。`contextlib.ExitStack` 可以登记动态数量的退出动作，下面用无故障的小例子观察它的顺序。

```python
from contextlib import ExitStack

events = []

def release(name):
    events.append("归还" + name)

with ExitStack() as stack:
    for name in ["电源", "闸门", "记录器"]:
        events.append("取得" + name)
        stack.callback(release, name)
    events.append("工作")

print(events)
```

输出先是取得电源、闸门、记录器和工作，之后依次归还记录器、闸门、电源。这里没有打开动作，也没处理本课要求的多错误组合。`ExitStack` 能帮忙组织清理，不意味着直接使用它就自动满足当前全部错误合同；使用库工具时仍要核对它如何传播多个错误。

本课在工厂迭代器取下一项、工厂调用、打开和业务块任何位置失败，都要停止取得后续资源。已经取得的资源仍逆序关闭，各一次。某个 `close` 失败，后面的关闭仍必须继续；否则坏记录器会让闸门和电源一起泄漏。

## 故障不是只保留最后一句话

假设 A 打开成功，B 取得后打开失败；关闭 B 又失败，关闭 A 也失败。C 不应被询问，业务块不运行。最后需要保存三份原错误：B 的打开错误、B 的关闭错误、A 的关闭错误。顺序反映主要失败与实际清理顺序。

没有清理错误时，原主要错误单独传播，保留同一个对象；没有主要错误且只有一个清理错误，也直接传播原对象。两个或更多错误则放进 `BaseExceptionGroup`，主要错误若存在排第一，后面跟各次关闭错误。组内要保留异常对象，不能只留下文字。它可容纳控制信号；若成员全是普通异常，构造时可以得到更具体的 `ExceptionGroup`。

这还解释了为什么一个简单的 `finally: close_everything()` 不足以证明实现正确：清理函数遇到第一个错误就退出，既会遗漏其他资源，也可能覆盖主要错误。你要同时观察每个资源是否尝试关闭、顺序是否正确以及最后保留了哪些异常。

工厂可迭代对象的 `StopIteration` 表示正常耗尽；不要让工厂、`open` 或 `close` 用它冒充业务故障。生成器式管理器里漏出的终止信号可能被 Python 转成 `RuntimeError`，原因链留着原信号。这种非法协议用法不属于“业务错误保持原身份”的承诺。各次管理范围也不能共享一份残留资源列表，否则第二次进入会关掉上一次的设备。

这些检查使用内存资源。关闭连接不会撤销已经升起的闸门或发布的数据，也不证明真实操作系统在进程被强制终止时会完成同样清理。

## 独立任务：先准备三份报告，再逐份发布

新任务先取得若干临时输出资源，全部准备好后才按原顺序发布。第二份发布可能失败，而第一份已经对外可见；失败以后停止发布，仍逆序关闭所有取得的资源。关闭临时资源不会撤销已发布的报告。

先设计返回或错误信息怎样让调用者知道哪些报告已发布，再写事件记录与故障注入。至少覆盖准备失败、第二份发布失败、发布与两次关闭同时失败，以及零份报告。解释为什么“所有资源都关闭了”不等于“全有或全无”。这里新增发布进度与部分成功的表达，需要自行运行、由人检查；原课程通过不会替这项业务策略记分。
