# 报告写出去之前，先读完最后一张收据

货运员拿着旧报告等更新。新CSV前九行都正常，最后一行数量却写成了“待定”。如果程序打开目标文件就开始写，旧报告可能早被清空，最后却没有一份可用的新报告。处理顺序本身就是这次交付的一部分。

你已会CSV解析、命令参数与测试。现在把纯数据处理接到文件上：读取源文件，完整校验并汇总，成功后写目标文件，最后返回报告数据。`open_file` 是调用者交给你的打开文件函数，允许你在受限环境中按给定路径读写；不要绕过它调用自己找到的路径。

## 关闭资源与保存旧内容是两件事

下面在普通Python中用内存文本流观察关闭。它演示with的退出行为，不模拟磁盘写入保证。

```python
from io import StringIO

source = StringIO("12\nbad\n")
try:
    with source:
        for line in source:
            print(int(line))
except ValueError:
    print("停止处理")
print(source.closed)
```

输出12、停止处理、True。第二行转换抛错后，with仍会关闭流。`with` 管理对象的进入与离开；对文件来说，退出时关闭句柄。但它不会自动恢复你已经覆盖的目标文件。把写目标的with放在校验前，仍可能损坏旧报告。

本课读取真实UTF-8文本，CSV读入时指定 `newline=''`，让csv模块处理记录换行。表头必须恰好item、qty。名称非空白但保留原文，整数数量可以是零或负数，同名累计后为零也保留。坏字段数量、坏表头、坏数量和损坏引号都以ValueError报告，与上一课CSV规则一致。

## 两个阶段之间有一道明确界线

先在自己拥有的内存字典里得到完整结果。直到输入遍历结束、最后一条也验证成功，才以写模式打开目标。写模式可能在打开时就截断旧文件，不能把“还没有write”当作旧内容安全的证据。

JSON应表达这个字典本身，而不是 `str(result)` 打出来的Python外观。JSON里的引号、布尔和空值规则与Python显示不同。使用json模块编码，目标再次解码后应得到相同数据；函数返回值也与这份报告一致。源文件只读，所有实际打开的源、目标句柄在成功和失败出口都关闭。

检查时故意把坏数量放到最后，再比较目标文件与运行前的旧文本是否完全一致。只检查异常类型，无法发现“抛对异常但先毁掉旧报告”。另测含逗号或换行的商品名、两张相反数量的收据和只有表头的空账，避免集成时丢掉解析层已经承担的规则。

这份练习保证坏输入不覆盖旧目标，不承诺写出途中磁盘满、电源中断或并发写入时原子替换。那需要临时文件、替换策略及失败恢复等额外设计，不能由with或JSON自动获得。

## 把报告拆成两份交付，先定义失败责任

另设计一个导出流程，同时产生汇总JSON和一份人读的缺货文本。先在内存中生成两份内容；再写下“第一份成功、第二份写失败时怎么办”的明确规则。可以选择临时文件准备后发布，或返回可重试状态，但不能宣称两次独立write天然同时成功。

用可注入的写入函数故意让第二次写失败，核对返回或异常、保留的文件以及重试时是否重复发布。你要评估多目标失败一致性，已超出本课单目标坏输入保护；请保存设计和故障记录作人工审查，不自动写入游戏成绩。
