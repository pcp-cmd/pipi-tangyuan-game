# 够数就关闸：最后一条交出去之前

汤圆只要两条符合条件的订单。第二条已经找到了，源却仍然开着，直到汤圆又调用一次 `next` 才关闭。看起来只晚了一步，但消费者得到足够结果后通常不会再来取，那一步可能永远不发生。

这课接在逐行货流之后：你需要理解生成器暂停、显式 `close`，以及内层生成器对源的所有权。环境已经提供 `stream_orders` 和 `OrderFormatError`，请复用它们；外层负责结束内层，内层负责关闭源。外层再直接关闭源，会造成重复归还。

## yield 的下一行可能很久不执行

先看一个故意把收尾放晚的小例子。它不是本课的解决方案，而是用来观察暂停点。

```python
events = []

def one_ticket():
    try:
        yield "末张票"
    finally:
        events.append("归还票夹")

tickets = one_ticket()
ticket = next(tickets)
events.append("旅客已拿到" + ticket)
print(events)
tickets.close()
print(events)
```

第一次输出只有 `['旅客已拿到末张票']`，第二次才多出“归还票夹”。消费者已拿到最后一项，清理却尚未发生。如果合同要求交付时资源已经归还，单靠包住 `yield` 的 `finally` 不能证明这个时点。

## 数的是通过筛选的订单

`take_matching(open_source, predicate, limit)` 按输入顺序交出最多 `limit` 条匹配项。判定函数 `predicate` 对每条读取到的订单只调用一次。未匹配的订单不占配额，匹配项才推进已交付数量。

`limit` 必须是严格的非负整数，不能是布尔值；验证发生在开始迭代时，而不是创建生成器时。`limit == 0` 时不打开源，也不调用判定函数。未开始就关闭，同样不打开。先把这三种时机写进测试，否则把外层写成普通函数再返回内部生成器，可能意外改变参数错误出现的时间。

达到第 `limit` 条匹配项时，要先关闭内层，再向外 `yield` 这最后一项。这样消费者一拿到它，清理条件就已经满足。达到配额之后不能多读一条“确认结束”：尾部如果是损坏订单，本课仍应成功返回已经足够的前缀。

相反，如果还没凑够，就应继续按需读取。耗尽源后结束；外层被消费者提前关闭，也要关闭内层。若判定函数或内层迭代抛错，保留原错误传播，同时完成收尾。这课沿用内层关闭不抛错的约定，不需要自行发明关闭失败覆盖规则。

## 三种计数能揭穿“差不多正确”

准备输入：不匹配、匹配 A、匹配 B、坏行，令配额为 2。记录读源事件、判定调用和源关闭。正确轨迹在交出 B 前已经关闭，既没读坏行，也没判定坏行。仅仅断言结果等于 `[A, B]`，无法发现关闭晚了或者偷偷预读的问题。

另一个反例是先取前两条再筛选。对于“不匹配、匹配 A、匹配 B”，它只交出 A，因为把输入条数当成匹配数量。还有一种是先把全部匹配项收集成列表再截取：结果可能碰巧正确，但按需读取和及时关闭都已经丢失。

这个模式适合有限的同步数据源。筛选条件执行产生的外部副作用不因最后结果被截断而回滚；判定函数尽量保持可观察、可测试，也要明确它会不会修改订单。

## 独立任务：取每个仓库的第一张订单

独立定义一个能关闭的同步订单迭代器，它每次给出已通过 id/qty 检查、另带 warehouse 字段的字典。这是迁移题的新输入接口，不能把新增字段塞进本课只接受 id/qty 的 `stream_orders`。warehouse 必须为非空字符串，否则抛 ValueError 并结束、关闭输入。新函数接收这份迭代器和严格非负整数 limit，取得其关闭责任；limit 为零时不读取，关闭后结束。

新需求是按输入顺序交出每个仓库首次出现的订单，最多覆盖 limit 个不同仓库。重复仓库的订单不交出，但仍算已读取。以 limit=3 为例，拿到第三个新仓库时，要先关闭输入，再交付最后一项；若总共只有两个仓库，则读到正常结束。输入 close 约定不抛错，其他读取错误保留原对象。

你需要同时维护“见过哪些仓库”和“交出多少个不同仓库”，不能再只用一个匹配布尔值。给出 `A、A、B、A、C、坏行` 的读取与关闭轨迹，并测试配额为零、外层提前关闭、仓库字段检查失败。请用实际事件断言证明尾部没读；这道迁移题需要人工复核，当前自动检查仍只针对原筛选合同。
