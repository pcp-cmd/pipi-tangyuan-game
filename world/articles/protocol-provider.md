# 可替换承运商：认能力，不认公司名

汤圆最初只接一家承运商，报价函数直接创建那家公司的对象。后来另一家公司报价更便宜，整个批量流程却要改。真正稳定的需求其实很小：给一张运单，返回以分为单位的整数报价。只要承运商提供这项能力，批量流程就不必知道它的内部算法。

开始前需要会定义类、调用对象方法、遍历列表，也要能解释已经验证过的 `Shipment`。本课提供这个类型供你使用，不需要重新实现它。再补一个区别：类型注解用于描述接口，不会自动验证每一次运行时返回值。

## Protocol 描述的是可用的操作

`typing.Protocol` 可以声明一类对象需要有哪些方法。符合方法约定的普通类不一定要继承这个协议。先看一个更小的时钟例子：使用者只依赖 `read()`，与具体时间来源分开。

```python
from typing import Protocol

class Clock(Protocol):
    def read(self) -> int:
        ...

class ManualClock:
    def __init__(self, minute):
        self.minute = minute

    def read(self):
        return self.minute

def next_minute(clock: Clock):
    return clock.read() + 1

print(next_minute(ManualClock(8)))
```

输出 `9`。`ManualClock` 没有继承 `Clock`，但有这里需要的操作。运行成功说明这次对象调用成立，并不等于已经运行静态类型检查器，更不等于所有写着 `Clock` 注解的对象都可靠。

本课的 `QuoteProvider` 需要声明 `quote(self, shipment: Shipment) -> int`。这能让代码阅读者与类型工具理解替换点。它不是“先判断属于哪家公司，再写一串分支”的名单；新的提供者只需遵守同一个能力约定。

## 一次报价要从头用到尾

`quote_batch(shipments, provider)` 按输入顺序处理运单，每张只调用一次报价方法，返回 `(identifier, cents)` 的列表。即使两张运单编号相同，也各自处理；本题没有授权你合并它们。

一个容易写出的错误是：调用一次 `quote` 检查类型，再调用一次组装结果。对于不断变动的报价器，两次可能不一样；即使一样，也多产生一次外部请求。应当围绕“这一次得到的结果”验证与组织输出，而不是反复向提供者取值。

金额要求严格的非负整数，以分为单位。`0` 是合法免费报价；`True`、`2.5`、`"200"`、`None` 和负数都无效，必须抛 `ValueError`。不要把它们强行转成整数以求继续。注解 `-> int` 不替你保证这些运行时条件；即便使用可运行时检查的协议，属性存在也不足以证明签名、返回类型或业务语义正确。

只要某张报价无效，就立即停止，后面的运单不再调用。提供者自己抛出的错误原样传播，不能换成笼统的“报价失败”。空列表应返回空列表，提供者零次调用。为了检查这些行为，可以让测试提供者按预定序列返回 `0`、`False`、`900`，并记录收到的运单：第二项无效后，第三项不应被访问。

如果第一次报价已经对外产生效果，后面的失败不会把第一次撤销。这份批量合同保证顺序和停止位置，没有承诺外部交易原子性，也不负责汇率与小数舍入。

## 独立任务：两家承运商逐单比价

为每张运单依次查询主、备两家承运商，各至多一次。有效报价中选较低者，相同价格优先主承运商；某家抛 `OSError` 时记录不可用，继续问另一家。非法返回值仍是接口错误，要立即停止整个批次。两家都不可用时，在该运单结果中明确标为“无报价”，不要伪造零元。

这次你需要设计结果结构来同时表达选择与失败，不能沿用只有价格的单一结果。先列出一方免费、另一方不可用、同价、两方不可用、主方非法返回五组预期，再记录实际调用顺序与次数。让别人根据你的结果结构复述发生了什么。这项迁移需要自写测试和人工判断，当前课程不会自动验收。
