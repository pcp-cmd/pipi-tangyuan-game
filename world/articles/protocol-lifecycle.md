# 闸门钥匙：借到设备以后，谁负责归还

皮皮借了闸门控制器。控制器到手了，启动却只完成一半：指示灯亮起，电机检查失败。这时不能说“启动没成功，所以没有东西要关”。设备已经属于这段工作范围，部分打开的连接仍要归还。反过来，如果借用工厂根本没交出控制器，就没有可供关闭的对象。

开始前，你需要会读 `try`、`except`、`finally`，也要分清“函数返回一个对象”和“函数抛出异常”。异常也是对象；保留原错误，包含保留它的身份，而不只是重新造一个文字相同的错误。如果这部分陌生，先用一个会失败的小函数观察 `finally` 仍会执行，再继续下面的设备故事。

## with 把哪一段工作圈起来

`with` 使用上下文管理协议：进入范围，交出可用对象，离开时执行退出操作。`contextlib.contextmanager` 允许用生成器表达这个过程。生成器中的一次 `yield` 把控制权交给 `with` 块；块内正常结束，生成器从这里继续；块内抛错，错误会被送回这个 `yield` 所在处。

先运行一个只标记范围的小例子。它没有设备工厂，也没有双重故障处理，只观察控制权在哪里。

```python
from contextlib import contextmanager

events = []

@contextmanager
def marked_scope():
    events.append("进入")
    try:
        yield "借用牌"
    finally:
        events.append("离开")

problem = ValueError("工作失败")
try:
    with marked_scope() as token:
        events.append(token)
        raise problem
except ValueError as caught:
    print(caught is problem)
print(events)
```

输出 `True`，随后是 `['进入', '借用牌', '离开']`。退出动作发生了，工作仍然失败；它们并不矛盾。如果在 `yield` 周围捕获错误后没有再抛出，调用者可能误以为工作正常结束。因此，“总会清理”和“向调用者报告成功”必须分别考虑。

## 沿着取得资源的时刻划清责任

本课的 `managed_session(factory)` 每次进入时只调用一次无参 `factory`。工厂失败，直接传播同一个错误，不调用并不存在的资源的 `close`。工厂返回后，先执行这个资源的 `open`；成功才把**同一个对象**交给块内代码。即使对象的布尔值为假，它也已经被取得，不能用 `if resource` 判断归还责任。

本题的资源明确允许在 `open` 部分失败后关闭。因此，取得以后，无论启动失败、工作失败还是正常离开，都要尝试 `close` 恰好一次。这项约定来自这种设备的接口，并不是所有第三方资源都允许任意时刻关闭。接入新资源之前，要查清它在部分初始化后由谁收尾。

可以把每次借用写成事件序列：取得失败时只有 `factory`；启动失败时是 `factory → open → close`；工作失败时是 `factory → open → 工作 → close`。先写出预期，再用记录事件的假设备核对，往往比只看最后的报错更容易发现漏关或重复关闭。

## 归还也失败时，别丢掉第一份线索

常见写法把 `close` 放进 `finally`，却没有考虑它自己也可能抛错。假设工作抛出 `ValueError("指令损坏")`，关闭又抛出 `OSError("连接断开")`。只把最后一个错误交给调用者，就没有满足本题保留两份原错误的要求。

这课约定：只有一个错误，就传播那个原对象；主要阶段和清理阶段都出错，就把它们按“主要错误、清理错误”的顺序放进 `BaseExceptionGroup`。这里要认识 `Exception` 与 `BaseException` 的区别：`KeyboardInterrupt` 等控制信号属于后者，却不属于前者。清理仍要照顾这些离开路径，但不能把控制信号吞掉。使用能容纳它们的异常组，才能同时保存主要控制信号和清理故障。普通异常组成的组仍可能表现为更具体的 `ExceptionGroup`，不要只凭组的显示名称判断内容。

关闭只释放资源，不撤销设备已经执行的指令。闸门已经升起后，连接正常关闭，不会自动让闸门降下。浏览器里的设备也是可观察的内存对象；这课训练的是生命周期和错误传播，并没有实际控制宿主设备。

## 换成需要交接的录音任务

独立写一个录音范围：启动后产生临时录音，正常退出才调用 `publish`；录制失败时不发布。无论发布成功或失败，都要归还设备。设备取得以后允许关闭，发布不具有自动回滚能力。与本课相比，你增加了一个仅成功路径执行、却也可能失败的阶段。

先写清启动、录制、发布、关闭四处故障的事件顺序，再实现并注入同一个预先创建的错误对象。自查发布失败是否仍关闭、录制失败是否完全没发布、主要错误与关闭错误是否都保留。最后说明“发布已写出一半”为什么不能靠关闭修复。这道迁移题需要你自己运行并解释；当前课程检查不会替它记分。
