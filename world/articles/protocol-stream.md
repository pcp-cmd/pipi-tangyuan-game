# 逐行货流：有人来取，才打开仓门

港口每天收到一长串订单。皮皮通常只看前几条，如果程序为了返回一个列表先读完全部文件，后面的坏行会让前面本来可用的订单也拿不到，文件还会占着资源。这里更合适的约定是：消费者要一条，程序才读取到足够交出一条的位置。

你需要理解迭代器、`next`、`yield` 和 `try/finally`。含有 `yield` 的函数被调用时，先创建生成器对象；函数体要等迭代推进才运行。生成器暂停时，局部变量和所在位置会保留下来，下一次取值继续向前，而不是重新执行函数。

## 暂停不是结束

这个小例子没有订单格式，只展示一个范围什么时候真正开始、何时收尾。

```python
events = []

def messages():
    events.append("开始读取")
    try:
        yield "第一封"
        events.append("继续读取")
        yield "第二封"
    finally:
        events.append("结束读取")

stream = messages()
print(events)
print(next(stream))
print(events)
stream.close()
print(events)
```

依次输出空列表、“第一封”、只有“开始读取”的列表，最后是 `['开始读取', '结束读取']`。`close()` 让暂停的生成器走清理路径，第二封没有被读取。若消费者提前 `break`，但仍持有生成器引用，不能把它当作明确的关闭承诺；需要负责者显式结束这个范围。

## 本课读的是物理行，交出的是订单

`stream_orders(open_source)` 返回生成器。创建它不打开源；第一次迭代才调用 `open_source`。未开始就关闭，也不打开。取得的源可以逐行迭代，并带有 `close()`；本题保证它的关闭不会抛错。

空白行可以跳过，但它仍占一个物理行号。假设第一行空白，第二行是合法订单，第三行 JSON 损坏，错误应定位第三行，不能因为只交出过一个订单就说“第 2 行”。行号从 1 开始，每读到一行就对应那个原始位置。

每个非空行必须解出 JSON 对象，且只有 `id`、`qty` 两个键。`id` 是去空白后非空的字符串，`qty` 是严格正整数、排除布尔值。注意这里清理字符串是**为了检查**：返回的仍是解析出的原字典，`id` 原来的首尾空白应保留。把所有字符串顺手规范化，会悄悄改变上游提供的数据。

按需读取并不表示每次 `next` 恰好读一行：遇到空行，可能要继续读几行才能找到下一条订单；找到合法订单就要暂停。若第一行合法、第二行损坏，第一次 `next` 应交出第一条，不应提前触发第二行错误。把源先转为 `list` 或预取下一行，都会破坏这种观察顺序。

## 不同故障保留不同线索

JSON 解码和订单结构检查失败，要转成提供的 `OrderFormatError(line_number)`，并把原始解析或验证错误放在原因链中。调用者既能定位物理行，也能追查原始失败。这个错误类已由环境提供，不要另造同名替身。

源自身读取时抛出的 `OSError` 则是读源故障，不应伪装成订单格式错误；保留原对象传播。获取源失败时没有资源可关；获取成功以后，正常耗尽、显式关闭、格式错误、读源错误，都必须关闭这个源一次。别把“出错类型怎么翻译”和“谁负责释放源”混在一个宽泛的捕获里，否则很容易把磁盘故障包装成错误行内容。

这课处理同步、有限的文本源，没有承诺网络重连、无限流或异步读取。返回生成器的价值是按需推进和明确所有权，不是让所有输入问题自动消失。

## 独立任务：有问题的测量行也要继续看

设计一个按行读取测量数据的生成器。非空行格式为“设备号,温度”；合法行交出结构化测量值，格式错误则交出包含原物理行号的错误结果，继续后面的行。源读取故障仍终止并传播；消费者提前关闭时仍要关闭源一次。

这里把格式错误从“终止异常”改成了“可继续的输出”，你必须重新设计结果形状。用空行、合法行、坏行、再一条合法行组成输入，并在不同位置停止消费。自查物理行号、读取次数和关闭次数，再解释为什么 `OSError` 不能用同样方式假装成一条坏记录。需要自行运行与人工复核，本课判题不会自动覆盖。
