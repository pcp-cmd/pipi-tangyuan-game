# 请停船，也等绳索收好

汤圆喊“停船”，皮皮开始收绳。此时发动机不再接新指令，不代表码头已经没有人在工作。异步取消也是这样：发出请求、目标收到请求、目标清理、目标最终结束，是可以分别观察的时刻。

先完成等待回执与事件信号两课，能用 `Event` 标出工作已经到达的位置，并理解单资源管理中的 `finally`。这课只管理调用者明确交给你的 `asyncio.Task`；有权等待一个对象，不等于有权取消所有后台任务。

## 三个问题，用三个观察回答

`task.cancel()` 请求取消，目标通常在下一次可取消的等待处收到 `CancelledError`。`task.done()` 表示任务是否已经处于终态，正常返回、抛错、取消都算结束；`task.cancelled()` 则只说明任务是否以取消结束。

目标也可能处理取消后返回备用结果。以下例子专门展示这种行为，帮助你避免把“有人请求过取消”谎报为最终取消。它不是建议普通业务吞掉取消，也不是本课辅助函数的完整实现。

```python
import asyncio

async def main():
    entered = asyncio.Event()
    handled = asyncio.Event()
    allow_finish = asyncio.Event()
    fallback = []

    async def operation():
        entered.set()
        try:
            await asyncio.Event().wait()
        except asyncio.CancelledError:
            handled.set()
            await allow_finish.wait()
            return fallback

    task = asyncio.create_task(operation())
    await entered.wait()
    task.cancel()
    await handled.wait()
    print(task.cancelling(), task.done())
    allow_finish.set()
    result = await task
    print(task.done(), task.cancelled(), result is fallback)

asyncio.run(main())
```

在 Python 3.12 中，先输出 `1 False`，然后是 `True False True`。请求计数为 1 时，任务还未结束；最终它正常返回了原备用对象，没有处于取消终态。这里故意没有清除请求计数，用于观察计数与结果并不是同一件事。

`cancelling()` 记录 `cancel()` 次数减去 `uncancel()` 次数，不能当成“正在清理”的精确标签。捕获取消也不会自动把这个数归零。`uncancel()` 属于低层取消控制，不要为了让状态看起来干净，就擦掉调用者的请求。本文按 Python 3.12 解释，不把 3.13 改进的多重取消行为当作这里的保证。

独立例子在最外层使用 `asyncio.run`；游戏函数已经运行在事件循环中，应直接等待。`CancelledError` 继承 `BaseException`，普通 `except Exception` 不会捕获它；广泛吞掉 `BaseException` 同样会隐藏重要控制信号。

## 只请求需要的那一次

本课 `cancel_and_join(task)` 接收当前事件循环中的 Task。普通 Future 不符合本题入口，抛 `TypeError`；不能把当前调用者任务传给自己，抛 `ValueError`。这些拒绝不能先改掉目标的取消状态。

调用者进入时若已经有未撤销的取消请求，应向外传播 `CancelledError`，不能开始一轮新的目标操作。对合法的目标，只有它未结束且 `cancelling() == 0` 时才请求一次取消。已经请求取消的目标可能正等待收尾许可，再追加取消会打断它正在等待的 `finally`；已经结束的目标也不需要再请求。

随后等待实际终态。目标以取消结束，返回 `('cancelled', None)`；正常返回，交回 `('finished', 原结果对象)`。普通业务或清理错误仍传播原对象。不能只因为自己调用过 `cancel` 就直接返回取消标记，也不能把清理异常藏进 `None`。

为了验证“等到了”，让目标清理停在一道事件闸门，先确认清理已开始，再检查等待者尚未结束。允许清理后才检查最终结果。没有 `await` 目标，只发请求就退出，无法证明离开时已经收完绳索。

## 等待者自己也被取消时

等待期间，调用者可能另外收到取消。这个请求必须向外传播，不能误当作目标的正常取消结果。甚至目标处理了转发的取消并正常返回，调用者自己的取消也不能因此丢失。若目标此时另抛普通业务或清理错误，本课仍保留那个错误，不承诺所有多方竞态都有统一错误优先序。

直接等待目标时，等待者收到的额外取消可能传给目标，打断它原本正在等待的清理。因此，“等待完整清理”的承诺有明确条件：目标配合一次取消，没有新的外部取消干扰。这个练习不保证反复取消下的通用停机；也不能强杀不合作的协程、线程或进程。

还有一个边界：协程尚未迈出第一步就被取消，体内的 `finally` 从未进入，不会凭空执行。测试必须先用到达信号确认目标已经进入受保护范围，才能讨论那里的清理。也不要为了躲开取消而启动一个没人等待的后台清理任务，把责任留给未来。

## 独立任务：两条船互相等着停下

现在管理两个已启动任务 A、B。A 的清理要等 B 宣告停止，B 的清理也可能等待一个外部许可。设计停机流程：先向所有需要停止的目标发出请求，再等待各自终态；不要先完整等 A 才请求 B，否则 A 可能永远等不到 B 停止。

先定义两个目标中一个失败时最终怎样汇报，再记录请求、进入清理、放行和结束的顺序。构造能让“逐个取消并等待”挂住的事件依赖，并证明你的新方案没有把清理留在后台。超时只用于防止实验永久挂住，不能替代事件证明。这里新增多个目标的协调和错误汇总，需要独立实现与人工检查，当前单目标课题不自动判定。
