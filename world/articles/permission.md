# 购买前先看许可

查看货架不会扣钱，购买会改变背包与余额。即使路由已经选中购买工具，程序仍要在操作发生之前确认许可。事后显示“没有批准”，不能撤销刚才已经发生的付款。

本课实现 `allowed(action, approved)`。`"view"` 可以直接进行，`"buy"` 只有在 `approved is True` 时允许，其他动作一律拒绝。函数始终交回 `True` 或 `False`，不执行动作。

## 真值和明确批准并不是同一条规则

条件语句可以把一个值当成真或假。例如非空文字和数字1通常会让 `if` 进入成立分支。许可合同却要求传来的值就是布尔值 `True`。

```python
permission_note = "同意"
print(bool(permission_note))
print(permission_note is True)
numeric_approval = 1
print(numeric_approval == True)
print(numeric_approval is True)
```

四行依次是 `True`、`False`、`True`、`False`。`bool` 问“这个值在条件中算真吗”，`==` 问“两个值是否相等”，`is True` 问“这个值是不是那个明确的布尔真值”。比较参数时应按当前合同选择规则，不能因为屏幕上看起来像“同意”就放行。

数字1与True的相等关系，不能替一张购买批准单。`"yes"`、`"True"`、非空列表同样不能代替布尔批准。这个精确区分是题目要求，不表示所有业务都要用相同的许可数据形状。

## 先选操作，再检查它的条件

查看不需要批准，所以 `allowed("view", None)` 也应允许。不要先拒绝所有非布尔approved，再检查action，那会给查看动作增加原合同没有的要求。

另一方面，`allowed("delete", True)` 必须拒绝。批准只能满足某个已知动作的条件，不能让任何陌生动作都合法。先写出允许的两种操作，再为各自列条件，最后给未知动作一个明确结果。

返回值也要检查。表达式有时会交回原来的字符串或数字，屏幕上看起来像“成立”，却不是布尔结果。运行检查时分别观察值与类型，不要只看某个分支有没有执行。

当前函数只处理眼前传入的布尔标记。真实购买还需要确认批准的是哪件物品、数量和价格，批准是否到期，以及执行前内容是否改变。这些内容会在“一次授权的一次航行”和原生可靠派送工程中继续练；本课通过不证明已经设计完一套授权系统。

## 批准一份确定的维修单

新任务写纯检查函数 `allowed_request(request, grant)`，始终返回布尔值，不执行操作。request 是字典，含 action 与非空字符串 device。action 为 `"view"` 表示读取设备说明，不需要费用或批准，grant 可以为 None；action 为 `"repair"` 时另需严格非负整数 fee，grant 必须是字典，含与当前请求相同的 device、fee 和严格为 True 的 approved。grant 的费用也须严格是非负整数，不能让布尔值混入比较。只有这些条件全部成立才允许维修；缺字段、字段类型错误、未知动作或非字典请求都返回 False，不修改输入。

先画出两种动作各检查哪些字段，再列出“批准后费用变化”“相同费用但设备不同”“批准字段为1”“缺少费用”四个反例。不能因为其中一个字段相同就执行，也不能把拒绝变成修改request来匹配grant。

这是人工核对的迁移练习，没有接入游戏购买。另写一个小调用方，只在检查返回 True 后调用一个计数器代替真实操作，证明允许路径执行一次、所有拒绝路径执行零次；纯检查函数自身始终零次执行。随后解释为什么检查必须放在操作之前。
