# 两份文件读完，才决定这批货能不能出库

库存CSV和订单CSV都可能重复记同一种货。你要先各自累计，再判断整批订单是否有缺口。如果先按第一行订单扣货，后面另一行又要同一种货，可能在尚未读完需求时就交出了错误报告。

这是独立交付任务，组合CSV、日志验证、回归测试和结算责任。函数通过传入的open_file读取两份真实UTF-8文件，完整校验后生成报告，写为JSON并返回同样数据。建议自己分出解析、计算与写出三种职责，让纯计算可以不依赖文件测试，文件边界也能单独注入坏数据。

## 空记录与空名称不是同一回事

下面在普通Python中观察csv读取器对三种记录的区分，不包含本课完整解析器。

```python
import csv
from io import StringIO

text = 'item,qty\n\n,0\n" ",2\n'
for row in csv.reader(StringIO(text, newline=""), strict=True):
    print(repr(row))
```

输出 `['item', 'qty']`、`[]`、`['', '0']`、`[' ', '2']`。表头后的完全空记录可以跳过；有两字段却名称为空或全空白，是坏数据，不能也跳过。合法名称只用strip检查空白，不删除它原来的首尾空格。

表头必须按序恰是item、qty，每行字段数正确，数量按整数文本转换且非负。这里与允许退货的CSV汇总课不同，负数量必须拒绝。引号内逗号和换行属于名称，交给csv处理；未闭引号或闭引号后多出字符均为坏CSV，应转为ValueError。两份文件各自同名累计，不能把库存和订单混在一个累计表里。

## 缺货报告与坏输入是不同出口

若有缺口，这是一份合法业务结果：status为shortage，stock保留原汇总库存，missing只列正缺口。不能先扣掉够用商品再报shortage，也不能只报告第一件缺货。

若所有需求足够，status为ready，stock是扣除后的新库存，missing为空字典。扣到零的键仍保留；订单里一个原库存没有的零数量键也在成功库存里保留为0。空表只有合法表头时可得到空汇总，两份都空也属于ready。

坏输入则不是shortage。任一文件中有坏表头、坏字段、负数或损坏CSV，抛ValueError，原报告内容保持。先把两份输入都读完且验证通过，才打开目标写模式；写模式可能在打开瞬间截断旧内容，不能边读取第二份边写目标。

## 可复查的结果，也包括退出后的文件状态

所有打开的句柄都要关闭，包括第二份文件最后一行失败时已经打开过的文件。源文件不得改变。报告使用JSON编码，重新解码得到的结构应与返回结果一致，而不是把Python字典的repr当作JSON写出。

为本项目设计测试时，至少分开验证同名累计、数量刚好够、多个缺口、全空表、含逗号换行的名字、零数量新键，以及库存或订单任一份最后一行损坏。失败测试要先放一份旧报告，再核对原内容保留，不能只看抛了什么异常。

本课保证校验失败时不覆盖旧报告，不承诺磁盘写入中断或多进程竞争时的原子交易。游戏中的通过也不等于你已经交付可维护的命令行工程。无答案多文件工程需要你自己拆模块、运行unittest与打包pyz，并保存对应运行记录；使用辅助与独立完成的证据保持各自含义。

## 加上预览与正式提交的双阶段协议

另设计一套交付流程：预览阶段读取库存和订单，给出报告与输入版本标识，不写正式报告；提交阶段只有输入版本仍相同时才发布，变化时拒绝并要求重新预览。先定义版本标识如何覆盖两份文件，以及空白、顺序或内容变化是否应触发失效。

用“预览后改订单”“预览后只改库存”“输入未变”的三条流程核对，注入一次写出失败再说明重试责任。检查预览无写入、旧计划不能覆盖新输入、正式结果仍遵守原缺口与零键规则。新题增加跨阶段有效性与发布责任，需要设计和实际故障记录作人工评估；当前判题没有验收这份协议。
