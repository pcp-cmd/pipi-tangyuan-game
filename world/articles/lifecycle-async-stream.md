# 不会偷偷续流的灯塔：停下画面，也要停下读取

海况源要等新消息。皮皮只要下一条，旧机器却提前把后面的消息都拉进缓存；汤圆点了停止，界面回到地图，后台还在读取。问题出在两个边界混了：一条数据什么时候才该被索取，以及离开时什么时候才算真正结束。

先会使用同步生成器与显式关闭，再完成 `async/await`、`Event` 和取消收尾课程。这里还需要异步迭代的三个动作：`__aiter__` 取得异步迭代器，`__anext__` 提供下一项的可等待操作，`StopAsyncIteration` 表示正常结束。`anext(iterator)` 取得一次这样的操作，等待以后才得到那一项。异步源本身与它返回的迭代器可能是不同对象。

## 暂停的时候，生产者没有新的读取许可

带 `yield` 的异步函数创建异步生成器。调用时只得到对象，不会因为“创建了流”就取得源；消费者第一次等待 `anext` 才开始推进。每次得到一项后，生成器暂停，后面代码等下一次需求才继续。

下面没有外部源，只观察一个异步生成器与消费范围。它用于原生 Python 3.12 文件；游戏任务函数里不要再嵌套 `asyncio.run`。

```python
import asyncio
from contextlib import aclosing

async def main():
    events = []

    async def readings():
        events.append("开始")
        try:
            yield 0
            events.append("继续取下一条")
            yield 7
        finally:
            events.append("清理")

    stream = readings()
    print(events)
    async with aclosing(stream):
        async for value in stream:
            events.append("消费" + str(value))
            break
    print(events)

asyncio.run(main())
```

输出空列表，然后是 `['开始', '消费0', '清理']`。零正常交给了消费者，第二条没有读取；`aclosing` 在消费范围退出时等待 `stream.aclose()`。这里只是消费者如何明确结束生成器，不是本课拥有外部源的完整实现。单独 `break`，仍持有生成器引用时，不能据此保证立即关闭。

## 谁取得源，谁承担归还

本课 `stream_owned(open_source)` 第一次需求才等待无参 `open_source()`。尚未开始就 `aclose()`，不应调用 opener。opener 成功返回后，生成器拥有那个源对象；此后即使创建异步迭代器失败，也要等待源的 `aclose()` 完成。最终关闭的是源，不是随意改成 `__aiter__` 返回的另一个对象。

如果 opener 失败，外层还没有拿到源，保留原错误即可。opener 若在内部已经部分取得别的资源，应由它处理自己的失败清理；调用者无法猜测一个没有返回的对象。

每次真实需求只拉取一项，交出同一个结果对象。`0`、`False`、`None`、空字符串都是数据，不是终止标记。先异步读完整个源再逐项 `yield`，即使外形仍像生成器，也违反了不预读的要求。

正常耗尽、消费者显式 `aclose()`、消费者用 `athrow()` 把错误送进生成器、读源失败，都需要等待已拥有源的异步关闭恰好完成一次。`athrow` 可以理解为：消费者不请求正常继续，而让暂停处收到一个错误。它让失败从消费一侧进入，同样不能绕过资源责任。

## 取消是一个会经过清理的退出原因

读取等待期间收到一次取消时，要保留 `CancelledError`，不能把它吞掉继续读下一条。已经拥有的源仍需异步关闭；如果关闭正在等另一个事件，外层操作此时还不能向调用者表现为已经完成。清理结束后才交代最终取消或故障。

清理成功，原读取或消费者错误保持身份传播；只有清理失败，就传播原清理错误；主要错误或取消与清理同时失败，就以 `BaseExceptionGroup` 按“主要、清理”顺序保存两个原对象。`aclose()` 引起的 `GeneratorExit` 是正常关闭控制，不作为额外业务错误塞进组。若这次正常关闭的清理失败，只留下清理错误。

要证明这件事，可以把源的读取和关闭各拦在一道 `Event` 闸门前。确定读取已经开始后取消等待任务，再等“关闭已开始”的信号；关闭许可还没发出时，断言任务未结束。放行后检查关闭一次、没有后续读取、取消仍可见。固定睡眠不能证明这个因果关系。

本题只覆盖打开或读取等待期间的一次合作取消。清理阶段再收到新取消、关闭永久卡住、进程被强制终止，都需要更强的退出约定。`shield` 保护某个被包住的任务，也不自动替外层等待它完成；不能据此宣称任何情况下都不会泄漏。

终止信号也有专门用途：`__anext__` 的 `StopAsyncIteration` 表示耗尽；opener 和 `aclose` 应用领域错误报告故障，不能拿迭代终止信号替代。在协程或异步生成器边界，这些非法漏出的信号可能变成带原因链的 `RuntimeError`，不属于普通业务错误原样传播的输入域。

## 独立任务：十条一份摘要，只要三份

写一个消费无限温度源的异步生成器，每十条交出一份包含最小值、最大值和平均值的摘要。消费者只取三份后关闭。每份摘要必须只读取对应的十项；取到第三份时，不应悄悄开始第 31 项。消费者显式关闭、读取失败或一次取消时，都要等待拥有的源收尾。

自己规定源不足十项就结束时怎样处理尾批，并把规则写进测试。使用事件记录证明读取上界、摘要顺序、故障位置与关闭次数，再让清理停在闸门处观察外层是否提前结束。这次新增分批状态和尾批政策，需要独立实现及人工核对；本课的单项货流检查不会自动证明你掌握了聚合。
